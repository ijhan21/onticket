19장. API 서버 배포 — Cloudflare Workers

이 장이 끝나면: 온티켓 API 서버가 인터넷에서 요청에 응답한다. 내 컴퓨터가 꺼져 있어도 https://onticket-api....workers.dev 의 공연 목록 조회가 응답한다. 시크릿을 Workers 시크릿으로 안전하게 등록하고, 배포 후 실제 주소로 검증하는 법을 익힌다.

19.1 개념 — 내 컴퓨터 밖에서도 서비스를 제공한다

개발과 배포의 경계

지금까지 온티켓은 localhost, 즉 내 컴퓨터 안에서만 실행됐다. 노트북을 닫으면 서비스도 멈춘다. 배포(deploy) 는 이 코드를 인터넷에 연결된 서버에서 실행해, 내 컴퓨터와 무관하게 24시간 응답하게 만드는 일이다. 오대표도 고객도 인터넷을 통해 접속할 수 있게 된다.

여기서 잠깐 localhost라는 말을 뜯어 보자. local은 '이 지역의, 여기의'라는 뜻이고 host는 '서비스를 제공하는 컴퓨터'를 가리킨다. 그러니까 localhost는 "바로 이 컴퓨터"라는 뜻의 특별한 주소다. 브라우저에 localhost:8787을 치면 '지금 사용하는 노트북에서 실행 중인 서버'로 연결된다. 이 주소는 내 컴퓨터를 벗어나지 못한다. 옆자리 동료가 자기 노트북에서 같은 주소를 쳐도 내 서버가 아니라 자기 컴퓨터를 가리킨다. 오대표에게 "여기 들어가 보세요" 하며 localhost 주소를 넘길 수 없는 근본 이유가 이것이다. 그 주소는 받는 사람마다 다른 컴퓨터를 뜻하니까.

'배포(deploy)'라는 단어도 짚어 두면 개념이 또렷해진다. deploy는 원래 군사 용어로 부대를 진지에 배치한다는 뜻이다. 대기하던 병력을 실제 작전 위치에 내보내는 것 — 소프트웨어에서도 비슷한 뜻으로 쓰인다. 내 컴퓨터에서 개발한 코드를 인터넷에 연결된 서버에 배치해 고객이 사용할 수 있게 하는 일이 배포다. 한국어로는 '띄운다', '올린다', '배포한다'가 모두 같은 뜻으로 쓰인다.

'내 컴퓨터에서는 되는데'는 개발 현장에서 가장 유명한 변명이다. 영어권에는 "It works on my machine(내 컴퓨터에서는 됩니다)"라는 관용구가 아예 농담으로 굳어져 있다. 왜 이게 문제냐면, 내 컴퓨터에서 잘 동작하더라도 배포 환경에서 같은 결과가 나오는지는 따로 확인해야 하기 때문이다. 내 컴퓨터에는 내가 깔아 둔 프로그램, .env 파일에 적어 둔 비밀 값, 열려 있는 포트가 있다. 인터넷의 서버는 그것들이 하나도 없는 백지 상태다. 배포란 "내 컴퓨터에서만 되던 것"을 "내 컴퓨터에 의존하지 않고 인터넷에서 접속할 수 있는 상태"로 전환하는 일이고, 이 장에서는 배포한 서비스가 실제로 동작하는지까지 확인한다.

배포할 때는 개발할 때보다 더 신중해야 한다. 로컬에서 생긴 오류는 나만 보지만, 배포된 서비스의 오류는 고객이 겪는다. 그래서 배포는 되돌릴 수 있는 방식으로, 확인하며 한다 — 이 장의 절차가 그 원칙을 담는다.

배포할 때 주의가 필요한 이유를 구체적으로 살펴보자. 개발 중에 코드가 깨지면 화면이 빨개지고 나 혼자 한숨 쉬면 그만이다. 하지만 배포된 서비스가 깨지면, 그 순간 리버사이드 재즈 티켓을 사려던 고객이 하얀 에러 화면을 본다. 결제 직전에 서버가 죽으면 고객은 "돈이 나갔나 안 나갔나" 불안해하며 고객센터에 전화한다. 배포 중 생긴 문제는 고객에게 직접 영향을 준다. 그래서 이 장에서는 배포 전에 점검하고, 배포 후에 검증하는 순서로 진행한다.

[짚고 가기] 이 장에서는 배포의 의미를 직접 체감할 수 있다. 지금까지 localhost만 봐 왔기 때문에, "내 노트북을 닫아도 남이 접속할 수 있다"는 것이 머리로는 이해돼도 몸으로는 실감하기 어렵다. 그래서 실습 마지막에 로컬을 끄고 확인하는 대목이 이 장의 하이라이트다. "노트북을 닫고 커피를 마시러 가도 고객이 온티켓을 이용할 수 있다"는 그 순간을 목표로 삼으면, 다소 지루할 수 있는 점검 절차도 목적을 갖고 따라가게 된다.

왜 API 서버를 먼저 배포하나

분리형이라 배포도 둘이다(API 서버, 프론트엔드). 순서는 API 서버가 먼저다. 프론트엔드는 "API가 어디 있는지"를 알아야 완성되기 때문이다. API 서버를 먼저 배포해 공개 주소를 확보하고, 그다음에 프론트엔드가 그 주소로 요청을 보내도록 설정한다. 집을 짓고 주소를 받은 뒤, 그 주소를 명함에 적는 순서다.

'분리형'이라는 말을 복습하자. 온티켓은 화면을 그리는 쪽(web, 프론트엔드)과 데이터를 다루는 쪽(api, 백엔드)을 아예 다른 앱으로 나눠 만들었다. 프론트엔드는 브라우저에 예쁜 화면을 띄우고, 고객이 "예매" 버튼을 누르면 뒤에서 API 서버에게 "EV009 티켓 두 장 주문할게"라고 물어본다. 즉 프론트엔드는 API 서버에게 말을 거는 고객이고, 말을 걸려면 상대방의 주소(전화번호)를 알아야 한다. 그 주소가 아직 없으면 프론트엔드는 "누구한테 주문을 넣어야 하지?"를 몰라 완성될 수 없다. 그래서 순서가 API 먼저인 것이다.

다른 예로 생각해 보자. 배달 음식점을 여는 상황이라고 하자. 주방(API 서버)이 먼저 실제 위치를 잡고 가게 주소를 받아야, 전단지(프론트엔드)에 "주문 전화: 02-...번"을 인쇄할 수 있다. 주소도 없는데 전단지부터 돌리면, 고객이 전화를 걸 곳이 없다. 반대로 주방 주소만 있고 전단지가 아직이면 문제가 덜하다 — 아는 사람은 주소로 직접 찾아올 수 있으니까. 그래서 주소를 가진 쪽(API)을 먼저 배포하고, 그 주소를 사용할 프론트엔드를 다음에 연결한다.

한 가지 오해를 풀어 두자. "API를 먼저 배포한다"는 것이 "프론트는 나중에 대충 해도 된다"는 뜻은 아니다. 순서의 문제일 뿐, 둘 다 배포되어야 고객이 화면을 보고 예매까지 할 수 있다. 다만 의존의 방향이 프론트→API 한쪽이라, 프론트엔드가 사용하는 API 서버를 먼저 배포하는 것이 자연스럽다는 이야기다.

이번에도 전부 프롬프트로

api 뼈대를 만들 때 wrangler.toml이 함께 생겼다. 이 장에서 하는 배포도 명령과 설정으로 이루어지므로 AI가 실행한다. 사람의 일은 셋이다 — 클라우드에 로그인하고, 시크릿을 직접 등록하고, 배포 결과를 검증하는 것.

이 셋을 관통하는 원칙은 첫 지시를 내리던 날부터 이어져 온 것과 같다 — 되돌리기 어렵거나, 권한이 필요하거나, 비밀값을 다루는 일은 사람이 직접 처리한다. 나머지 반복 노동(빌드, 업로드, 명령 조합)은 AI에게 맡긴다. 각각이 왜 사람의 일인지 미리 짚어 두자.

  • 로그인 — 로그인은 "이 컴퓨터에게 내 클라우드 계정을 다룰 권한을 준다"는 결정이다. 아무 프로그램이나 내 계정에 배포하게 둘 수는 없으니, 브라우저에서 내가 직접 "이 도구를 승인합니다" 버튼을 누른다. 맨 처음 Claude Code에 로그인하던 것과 똑같은 구조다.
  • 시크릿 등록 — 시크릿은 DB 비밀번호가 든 연결 문자열, 결제사 시크릿 키 같은 값이다. 이 값을 AI에게 "이거 올려줘" 하며 채팅창에 붙여넣는 순간, 그 비밀은 대화 기록에 남는다. 그래서 값 자체는 사람이 자기 손으로 등록하고, AI는 "어떤 명령으로 넣으면 되는지"까지만 안내한다.
  • 검증 — "배포됐습니다"라는 AI의 말은 보고일 뿐, 증명이 아니다. 실제로 그 주소가 응답하는지, 데이터가 나오는지는 사람이 눈으로 확인해야 끝난다.

[짚고 가기] "AI가 배포까지 다 하면 나는 뭘 배우나?" 싶을 수 있다. 답은 명확하다 — 배포의 '판단'을 배운다. 언제 올려도 되는지(점검), 무엇을 비밀로 지켜야 하는지(시크릿), 올린 뒤 무엇을 확인해야 하는지(검증). 명령어 wrangler deploy를 외우는 건 5초짜리 지식이지만, "CI 검사에 실패한 코드는 배포하지 않는다", "배포 성공 여부는 검증으로만 확인된다" 같은 판단은 평생 가는 감각이다. 이 장에서 가져가야 할 것은 명령이 아니라 이 세 가지 판단이라는 점을 기억해 두자.

19.2 용어 정리

이 장에서 처음(또는 다시) 만나는 용어들이다. 배포는 낯선 단어가 특히 많이 쏟아지는 구간이라, 여기서 한 번 정확히 잡고 실습으로 들어가면 훨씬 매끄럽다. 완벽히 외울 필요는 없다 — "이런 게 있구나" 정도로 눈에 익혀 두면 된다.

엣지 배포와 Cloudflare Workers (복습+심화)

아키텍처를 결정할 때 정했듯 API 서버는 Cloudflare Workers에 올린다. Workers의 특징을 배포를 앞두고 다시 짚자.

  • 서버리스: 서버 기계를 빌려 관리하지 않는다. 코드만 올리면 요청이 올 때 실행된다. 놀고 있을 때 드는 비용이 없다
  • 엣지(edge): 전 세계에 퍼진 Cloudflare 서버 중 고객과 가까운 곳에서 실행된다. 서울 고객은 서울 근처에서 응답받아 빠르다
  • 잠들지 않음: 일부 무료 호스팅과 달리 첫 요청이 느리게 깨어나는 일이 없다. 티켓 오픈처럼 순간 몰리는 서비스에 중요하다
  • 무료 한도: 하루 10만 요청 — 온티켓 초기에 충분하다

네 가지를 하나씩 풀어 보자.

먼저 Cloudflare라는 회사부터. 전 세계 수백 개 도시에 자기네 서버(데이터센터)를 깔아 두고 방문자를 가장 가까운 서버로 연결해 주는 회사인데, Workers는 바로 그 서버망 위에서 우리 코드를 돌려 주는 서비스다.

서버리스(serverless) — 직역하면 '서버가 없는'이지만, 서버가 정말 없다는 뜻이 아니라 서버를 내가 빌리고 관리하지 않아도 된다는 뜻이다. 전통적인 방식에서는 서버 한 대를 통째로 빌려서 고객이 오든 안 오든 24시간 켜 두고 요금을 냈다. 서버리스는 요청이 들어오는 순간에만 코드가 잠깐 실행되고, 안 들어오면 아무 일도 없다. 온티켓처럼 티켓 오픈 때만 확 몰리고 평소엔 한산한 서비스에 잘 맞는다.

엣지(edge) — '가장자리'라는 뜻인데, 네트워크의 가장자리, 즉 고객과 가장 가까운 지점을 말한다. 서버가 한 곳(예: 미국 어느 데이터센터)에만 있으면 서울 고객의 요청이 태평양을 건너갔다 와야 한다. 엣지 방식은 코드를 전 세계 서버에 미리 복사해 두고 서울 고객의 요청은 서울 근처 서버가 응답한다. 거리가 짧으니 응답이 빠르다.

잠들지 않음 — 무료 호스팅 중에는 오래 요청이 없으면 서버를 잠재웠다가 다음 고객이 왔을 때 깨우느라 첫 응답이 몇 초씩 걸리는 것들이 있다. 이 현상을 콜드 스타트(cold start) 라 부른다. Workers는 이 지연이 사실상 없다. 티켓 오픈 순간에 "첫 고객만 몇 초 기다린다"는 상황조차 티켓 서비스에는 치명적이라 이 성질이 중요하다.

무료 한도 — 하루 10만 번의 요청까지 무료다. '요청'은 API를 한 번 호출할 때마다 하나씩 센다. 하루 10만이면 초기 온티켓에는 넉넉하다.

왜 하필 Workers인가, 다른 선택지와 비교하면 이렇다.

배포 방식 특징 온티켓에 맞나
Cloudflare Workers 서버리스·엣지·콜드 스타트 없음·무료 한도 넉넉 API 서버로 채택
전통 VPS(서버 한 대 임대) 자유도 높지만 직접 관리·24시간 요금 관리 부담이 큼
다른 서버리스(콜드 스타트 있음) 저렴하나 첫 응답이 느릴 수 있음 티켓 오픈에 불리

이 표의 핵심은 "정답이 하나"라는 게 아니라, 우리 상황(티켓 오픈에 몰림 + 관리 인력 없음 + 예산 최소)에 Workers가 잘 맞았다는 것이다. 다른 서비스라면 다른 선택이 나올 수 있다. 도구는 상황에 맞춰 고르는 것이지, 좋은 도구가 따로 정해져 있는 게 아니다.

프로덕션 / 스테이징

  • 프로덕션(production): 진짜 고객이 쓰는 실서비스 환경
  • 스테이징(staging): 프로덕션과 똑같이 만든 연습·검증용 환경

큰 회사는 스테이징에서 먼저 확인하고 프로덕션에 올린다. 온티켓 첫 배포는 프로덕션 하나로 단순하게 가되, 개념은 알아 두자 — "실전에 올리기 전에 똑같은 무대에서 리허설한다"는 발상이다.

용어의 뜻을 조금 더 풀어 두자. 프로덕션은 원래 '생산, 제작'이라는 뜻이지만, 소프트웨어에서는 실제로 돌아가며 고객을 상대하는 진짜 환경을 가리킨다. 공연으로 치면 관객이 앉아 있는 '본 공연'이다. 여기서 실수가 나면 관객이 본다. 스테이징(staging) 은 'stage(무대)'에서 온 말로, 본 공연과 똑같이 꾸며 놓은 리허설 무대다. 조명도 음향도 본 공연과 같게 맞춰 두고, 관객 없이 먼저 돌려 보며 문제를 잡는다. 리버사이드 재즈 페스티벌을 여는데 관객 앞에서 처음 합을 맞추지는 않는 것과 같다 — 사전 리허설에서 걸러 낸다.

왜 이 둘을 나누느냐면, 고객이 보기 전에 실수를 걸러 낼 안전지대가 필요하기 때문이다. 새 기능을 프로덕션에 바로 올렸다가 버그가 나면 고객이 피해를 본다. 스테이징에 먼저 올려서 똑같은 조건으로 확인하고, 문제없으면 프로덕션에 올린다. 온티켓은 아직 규모가 작아 프로덕션 하나로 단순하게 가지만, 서비스가 커지면 반드시 이 리허설 무대를 만들게 된다. 지금은 "그런 발상이 있다"만 알아 두면 충분하다.

[짚고 가기] 스테이징을 지금 만들지 않는 이유는 "게을러서"가 아니라 "규모에 맞춰서"다. 고객 없는 첫 배포에 무대를 둘씩 짓는 것은 오히려 과한 준비다. "필요해지면 그때 만든다"는 것도 엄연한 실무 판단이다. 이렇게 생각하면 '정석대로 안 하면 잘못'이라는 강박에서 벗어날 수 있다. 반대로 온티켓이 고객을 받기 시작한 뒤라면, 스테이징 없이 프로덕션에 바로 올리는 것은 위험하다는 점도 함께 기억해 두면 균형이 잡힌다.

시크릿을 클라우드에 등록하는 법

로컬에서 api는 .env의 DATABASE_URL로 DB에 접속했고, 결제를 붙일 때 같은 .env에 넣은 토스 시크릿 키로 결제를 승인했다. 배포된 Workers는 내 .env를 볼 수 없다(그 파일은 저장소에도 없다 — 훅이 지켰다). 그래서 Workers의 시크릿 저장소에 따로 등록한다. 시크릿이 둘이니 명령도 두 번이다.

터미널
$ wrangler secret put DATABASE_URL
$ wrangler secret put TOSS_SECRET_KEY

둘째 줄의 이름은 예시다. 토스 시크릿 키의 환경변수 이름은 결제를 붙일 때 AI가 붙였으므로, api/.env.example에 적힌 이름 그대로 쓴다. 이름이 한 글자라도 다르면 코드는 그 값을 찾지 못한다.

명령을 하나 실행할 때마다 값을 입력하라는 창이 뜨고, 입력한 값은 Cloudflare에 암호화되어 저장된다. 코드에도, 저장소에도, 로그에도 남지 않는다. 앞에서 배운 로컬과 배포 환경의 환경변수 차이를 여기서 확인할 수 있다 — 같은 DATABASE_URL이 로컬에선 .env에서, 프로덕션에선 이 Workers 시크릿에서 공급된다. 코드는 어느 쪽인지 모른다.

이 부분이 이 장에서 개념적으로 가장 중요하니 천천히 풀어 보자.

먼저 시크릿(secret) 이란 무엇인가. 말 그대로 '비밀'이다. 코드가 돌아가려면 필요하지만, 남에게 보이면 안 되는 값들 — DB 접속 문자열(DATABASE_URL), 결제사 비밀 키, API 토큰 같은 것들이다. DATABASE_URL 안에는 DB의 주소와 아이디, 그리고 비밀번호가 통째로 들어 있다. 이걸 누가 보면 우리 데이터베이스에 그대로 접속할 수 있으니, 절대 새어 나가면 안 되는 값이다.

그럼 배포된 Workers는 이 값을 어디서 얻나? 로컬에서는 .env라는 파일에 적어 뒀지만, 그 파일은 내 컴퓨터에만 있고 저장소에도 안 올라간다. 왜 저장소에 안 올렸냐면, 시크릿이 코드와 함께 GitHub에 올라가면 전 세계에 비밀번호를 공개하는 꼴이기 때문이다. 앞에서 세운 보안 훅이 바로 이 사고를 막아 줬다 — '훅이 지켰다'는 그 뜻이다. 그런데 저장소에 안 올렸으니, 인터넷의 Workers는 내 .env를 볼 방법이 없다. 노트북 안의 파일이니까.

여기서 해법이 Workers 시크릿(Secrets) 이다. Cloudflare가 계정별로 제공하는 암호화된 비밀 저장소인데, 여기에 DATABASE_URL과 토스 시크릿 키 값을 따로 등록해 두면 배포된 코드가 실행될 때 그 값을 읽어 쓴다. wrangler secret put DATABASE_URL이 바로 "이 이름으로 시크릿을 등록하겠다"는 명령이다. 명령을 실행하면 화면에 값을 입력하라는 프롬프트가 뜨고, 여기에 실제 값을 붙여넣는다. 입력한 값은 암호화되어 저장되며 코드에도, 저장소에도, 화면 로그에도 남지 않는다.

여기서 시크릿의 성질 하나를 분명히 해 두자. 값을 등록할 수는 있지만, 한 번 등록한 값은 다시 꺼내 볼 수 없다. 등록 뒤에 볼 수 있는 것은 "DATABASE_URL이라는 이름의 시크릿이 있다"는 사실과 그 이름뿐이고, 안에 든 실제 값은 Cloudflare 대시보드에서도 wrangler 명령으로도 다시 표시되지 않는다. 값을 바꾸고 싶으면 같은 이름으로 wrangler secret put을 한 번 더 실행해 덮어쓰는 것이 유일한 방법이다.

이것은 고장이 아니라 설계된 동작이다. 누가 계정 화면을 들여다봐도, 화면 로그가 어딘가에 남아도, 비밀번호 자체는 보이지 않는다. 대신 사람 쪽에 책임이 하나 생긴다 — 값을 잊었을 때 "등록해 둔 시크릿에서 확인"은 선택지가 아니다. 원본은 언제나 다른 곳에 있어야 한다. 우리 경우엔 로컬 .env와, 값을 처음 발급받은 서비스의 대시보드(Supabase, 토스)가 그 자리다.

로컬 환경과 배포 환경에서 값을 가져오는 곳을 비교하면 차이가 분명해진다. 표로 정리하면 이렇다.

값이 어디서 오나 저장소에 올라가나
로컬(내 컴퓨터) .env 파일 안 올라감(훅이 지킴)
프로덕션(배포된 Workers) Workers 시크릿 파일이 아니니 애초에 대상 아님

핵심은 마지막 문장이다 — 코드는 어느 쪽인지 모른다. 코드에는 그냥 "DATABASE_URL이라는 이름의 값을 달라"라고만 적혀 있다. 그 이름표에 붙는 실제 값이 로컬에서는 .env에서, 프로덕션에서는 Workers 시크릿에서 온다(토스 시크릿 키도 똑같다). 코드는 값이 어느 환경에서 왔는지 구분할 필요가 없다. 그래서 코드를 한 줄도 고치지 않고 같은 코드를 내 노트북과 배포된 서버에서 실행할 수 있다. 이 '이름은 같고 값의 출처만 다르다'는 구조가, 시크릿을 코드 밖으로 빼내는 이유의 전부다.

[짚고 가기] 여기서 헷갈리기 쉬운 점 둘. (1) "그럼 로컬 .env랑 Workers 시크릿에 같은 값을 두 번 넣는 건가?" — 그렇다. 같은 DATABASE_URL을 로컬 .env에 한 번, Workers 시크릿으로 한 번 등록한다(토스 시크릿 키도 마찬가지). 로컬과 배포 환경에 값을 각각 등록하는 것이다. (2) "등록한 값이 틀리면?" — 배포는 되는데 DB 접속만(토스 키라면 결제 승인만) 실패한다. 그래서 뒤에 나올 '배포 후 검증'에서 실제 데이터가 나오는지를 반드시 확인하는 것이다. 이 두 가지를 미리 짚어 두면, 시크릿을 넣고 나서 검증까지가 한 흐름이라는 게 자연스럽게 이어진다.

배포 URL

배포가 끝나면 https://onticket-api.<계정>.workers.dev 같은 주소가 나온다. 이것이 API 서버의 인터넷 주소다. 이 주소에 공연 목록 조회, 주문 생성 같은 엔드포인트 경로를 붙여 요청하면 로컬에서와 같은 응답을 받는다 — 이제는 인터넷을 통해 누구나 요청을 보낼 수 있다.

이 주소를 뜯어 보면 배포가 무슨 일을 했는지 손에 잡힌다.

  • https:// — 암호화된 안전한 연결이라는 뜻. http가 아니라 https인 것은 고객과 서버 사이 통신이 도청되지 않게 암호화된다는 표시다. Cloudflare가 이 암호화를 자동으로 붙여 준다.
  • onticket-api — 우리 앱의 이름. wrangler.toml에 적어 둔 name이 여기로 온다. 처음 이 이름을 정할 때, 그것이 훗날 인터넷 주소의 일부가 된다는 걸 몰랐을 것이다. 지금 그 이름이 주소가 되어 돌아왔다.
  • <계정>.workers.dev — Cloudflare가 무료로 내어 주는 기본 도메인. 계정마다 다른 이름이 붙어, 다른 서비스와 겹치지 않는 고유한 주소가 된다.

localhost:8787과 이 주소를 나란히 놓으면 차이가 선명하다.

localhost 때 배포 후
공연 목록 조회 주소 http://localhost:8787 + 명세의 경로 https://onticket-api.<계정>.workers.dev + 같은 경로
누가 접속 가능한가 나만(내 컴퓨터 안) 누구나
내 노트북 꺼지면 응답하지 않는다 계속 응답한다
응답 내용 11개 공연 JSON 똑같이 11개 공연 JSON

주목할 것은 마지막 줄이다. 응답 내용은 똑같다. 배포가 코드를 바꾼 게 아니라 코드가 실행되는 환경을 바꾼 것뿐이기 때문이다. 같은 공연 목록 조회가 같은 데이터를 반환하되, 이제는 내 노트북 대신 배포된 서버가 응답한다. 이 '주소만 바뀌고 응답은 같다'는 것을 직접 확인하는 순간이 이 장의 실습에 있다.

참고로 나중에 온티켓이 자리를 잡으면 api.onticket.com 같은 내 도메인을 사서 이 기본 주소에 연결할 수 있다. 하지만 지금은 무료로 주어지는 workers.dev 주소로 충분하다. 도메인 구입은 배포와 별개의 일이고, 배포가 먼저 되어야 거기에 도메인을 이어 붙일 수 있다.

19.3 개념 — 배포 전 점검, 배포 후 검증

배포는 "명령 한 번"이 아니라 앞뒤로 확인이 붙는 절차다.

이 장의 제목만 보면 "wrangler deploy 한 줄 치면 끝 아닌가?"라고 생각하기 쉽다. 명령 자체는 정말 한 줄이다. 하지만 배포를 안정적으로 진행하려면 명령 실행 전후에 상태를 확인해야 한다. 앞에서는 "올려도 되는 상태인가"를 점검하고, 뒤에서는 "정말 올라갔는가"를 검증한다. 이 앞뒤 확인이 없는 배포는 눈 감고 던지는 것과 같다. 비행기 조종사가 이륙 전 점검표(checklist)를 읽고, 착륙 후에도 계기를 확인하는 것과 같은 규율이다.

배포 전 점검

  • CI 통과: main이 CI를 통과한 상태인가. 검사에 실패한 코드는 배포하지 않는다
  • 시크릿 준비: 프로덕션에 필요한 시크릿(DATABASE_URL, 토스 시크릿 키)이 등록돼 있나
  • 설정 확인: wrangler.toml의 이름·진입점이 맞나

세 가지를 왜 확인하는지 하나씩 보자.

CI 통과 — 'CI'는 코드가 올라올 때마다 자동으로 검사를 돌려 주는 장치다. 검사를 통과하면 초록불, 실패하면 빨간불이 뜬다. 배포 직전에 이 색을 확인하는 이유는 단순하다 — 검사 실패는 코드나 설정에 문제가 있다는 신호이고, 이 상태로 배포하면 고객에게도 영향을 줄 수 있다. "CI 검사에 실패한 코드는 배포하지 않는다"는 이 장에서 가장 짧지만 가장 중요한 규칙이다. 초록불을 확인하고 올린다.

시크릿 준비 — 용어 정리에서 봤듯, 배포된 Workers는 등록된 시크릿에서 값을 읽어 DB에 접속한다. 시크릿이 등록돼 있지 않으면 배포는 되는데 DB 접속만 실패한다. 겉으로는 서버가 떴는데 데이터를 못 불러오는, 가장 헷갈리는 상태가 된다. 그래서 배포 전에 "필요한 시크릿이 다 등록됐나"를 미리 확인한다. 온티켓의 api에는 시크릿이 둘이다 — DATABASE_URL과, 결제를 붙일 때 들어간 토스 시크릿 키. 토스 키를 빠뜨리면 목록 조회는 멀쩡한데 프로덕션에서 결제 승인만 실패한다. 승인 요청에 실을 키가 등록돼 있지 않기 때문이다. 외부 연동이 늘면 목록도 길어진다.

설정 확인 — wrangler.toml은 api 뼈대를 만들 때 생긴 '앱의 신분증명서'다. 여기 적힌 name(앱 이름)이 배포 주소가 되고, main(진입점)이 "어느 파일부터 실행할지"를 정한다. 이 값들이 틀리면 엉뚱한 이름으로 배포되거나 실행이 안 된다. 배포 전에 한 번 훑어 "이름·진입점이 맞나"를 본다.

이 셋을 점검표로 정리하면 이렇다.

점검 항목 확인 방법 통과 못 하면
CI 통과 GitHub의 main 최근 커밋이 초록인가 실패 원인부터 고치고 배포는 미룸
시크릿 준비 필요한 시크릿이 다 등록됐나 먼저 wrangler secret put으로 등록
설정 확인 wrangler.toml의 name·main이 맞나 설정을 바로잡고 배포

배포 후 검증

배포는 "됐다는 말"로 끝나지 않는다. 실제 주소로 요청을 보내 봐야 끝난다.

  • 배포 URL의 /health 가 응답하는가 (curl·브라우저)
  • DB에 연결됐는가 (실제 데이터가 나오는가)
  • 로컬을 끄고도 응답하는가 — 이게 배포의 증명이다

"배포했다"와 "배포가 됐다"는 다르다. 후자는 검증으로만 확인된다.

이 세 검증이 각각 무엇을 증명하는지가 중요하다.

첫째, 주소가 응답하는가. 배포 URL의 상태 확인용 주소 /health를 실제로 열어 본다. 브라우저 주소창에 붙여넣거나 curl이라는 명령으로 요청을 보내 본다. 응답이 오면 "배포된 서버가 동작하고 있다"는 것이 증명된다. 여기서 /health라는 주소를 잠깐 짚자 — 많은 서비스가 "나 살아 있어요"만 짧게 대답하는 전용 주소를 하나 둔다. 병원의 건강검진(health check)처럼, 서버가 정상인지 가볍게 물어보는 창구다.

둘째, DB에 연결됐는가. 서버가 떴다는 것과 DB가 붙었다는 것은 다르다. 공연 목록 조회가 빈 배열이 아니라 실제 11개 공연 데이터를 반환하면, 서버가 시크릿으로 등록한 DATABASE_URL로 DB에 제대로 접속했다는 뜻이다. 데이터가 안 나오면 십중팔구 시크릿이 안 올라갔거나 값이 틀린 것 — 시크릿을 설명하며 [짚고 가기]에서 예고한 바로 그 상황이다.

셋째, 로컬을 끄고도 응답하는가. 이것이 이 장의 절정이다. 앞의 두 검증까지는 내 노트북에서 로컬 서버가 돌고 있어도 통과할 수 있다(혹시 브라우저가 로컬을 보고 있었을 수도 있으니까). 하지만 로컬 서버를 완전히 끄고 나서도 배포 URL이 응답한다면, 그 응답은 내 노트북과 무관하게 배포된 서버에서 온 것이 확실하다. 이 비교를 통해 배포가 완료됐음을 확인할 수 있다.

'검증(verify)'이라는 말은 라틴어 verus(참된)에서 왔다 — 참인지 직접 확인한다는 뜻이다. "배포했다"는 것은 내가 명령을 내렸다는 사실이고, "배포가 됐다"는 것은 그 결과가 참임을 확인한 사실이다. 이 둘 사이의 간극이 바로 이 절의 주제다. AI가 "배포 완료했습니다"라고 보고해도, 그것은 명령이 끝났다는 보고일 뿐 배포된 서버가 실제로 응답한다는 증거는 아니다. 증명은 사람이 실제 주소로 요청을 보내 봐야 나온다. 첫날 배운 '검증은 사람의 일'이 배포에서 이런 모습으로 나타난다.

[짚고 가기] '배포 전 점검 + 배포 후 검증'은 비행기에 빗대면 기억에 잘 남는다. 조종사는 이륙 전에 점검표를 소리 내어 읽고, 착륙 후에도 계기를 확인한다. 배포도 똑같다 — "CI 검사에 실패한 코드는 배포하지 않는다(점검)"와 "실제 주소가 응답하는지 본다(검증)"가 앞뒤로 붙는다. 특히 "배포했다 ≠ 배포가 됐다"는 이 장 전체를 한 문장으로 압축한 문구다. 크게 적어 두고, "완료했습니다"라는 AI 보고만 믿고 넘어가려 할 때마다 "그건 '배포했다'지, '배포가 됐다'는 어떻게 확인하지?"라고 스스로 되물으면 습관이 잡힌다.

19.4 프롬프트 작성법 — 배포를 요청하는 절차

배포에는 사람이 직접 하는 일(로그인·시크릿 입력·검증)과 AI에게 맡기는 일(점검·빌드· 업로드)이 섞여 있다. 프롬프트를 쓸 때 지킬 원칙은 하나다 — 목표를 주되, 사람이 손대야 할 지점을 명시해서 AI가 그 선을 넘지 않게 한다.

배포 요청

프롬프트
api 서버 배포해줘

한 줄이다. 배포 전에 무엇을 점검할지, 배포 뒤에 무엇을 확인할지를 여기 적지 않았다. 적을 필요가 없어서다.

  • CI 통과 — 관문을 세울 때 만든 워크플로가 main에 push될 때마다 판정한다. 지금 main에 있는 코드는 그 관문을 지나온 것이다.
  • wrangler.toml 설정 — api 뼈대를 만들 때 생긴 파일이고, 배포 직전에 저장소에 올린다. AI가 읽는다.
  • 시크릿 등록 — 이 지시를 넣기 직전에 사람이 터미널에서 올리고 이름을 눈으로 확인한다.
  • 배포 뒤 확인 — AI에게 대신 호출시키지 않는다. 사람이 브라우저로 직접 연다. AI가 "배포 완료"라고 말하는 것과 주소가 실제로 응답하는 것은 다른 일이기 때문이다.

즉 조건을 프롬프트에 적는 대신 앞뒤 단계가 그 조건을 만들어 놓는다. 여기서 지시가 길어진다면, 그것은 앞 단계 어딘가가 비어 있다는 신호다.

프롬프트로 시키지 않는 것 — 로그인과 시크릿

로그인과 시크릿 등록은 프롬프트로 시키지 않는다. 명령 자체는 몇 줄뿐이지만, 하나는 권한을 넘기는 일이고 하나는 비밀을 다루는 일이라 사람이 터미널에서 직접 친다.

그래도 AI에게 물을 일은 생긴다 — "프로덕션에 필요한 시크릿 목록과 그것을 올리는 명령을 알려줘" 같은 것. 그때는 "값 입력은 내가 직접 한다" 를 한 줄 붙인다. 이 한 줄이 없으면 AI가 친절하게 "값을 알려주시면 제가 넣어 드릴게요"라고 나올 수 있고, 그 순간 비밀번호가 대화창에 남는다. 미리 선을 그어 두면 AI는 명령의 틀만 안내하고, 실제 값은 사람이 터미널 프롬프트에 직접 붙여넣게 된다. "AI는 명령까지, 비밀은 사람 손으로"를 프롬프트에 문장으로 심는 요령이다.

검증을 더 시키고 싶다면

사람이 브라우저로 확인하는 것 말고, AI에게 검증을 더 시킬 수도 있다. 그때 쓰는 지시는 이런 모습이다.

프롬프트
방금 배포한 주소({배포URL})로 API를 검증해줘. 로컬에서 확인했던 것 그대로 —공연 목록이 11개 나오는지, 공연 하나의 상세가 나오는지,남은 수량보다 많이 주문하면 여전히 409로 거절되는지. curl로 실제 호출한 결과를 보여줘.

{…} 자리만 실제 주소로 바꿔 입력한다.

이 프롬프트가 잘 짜인 이유는 눈으로 확인 가능한 사실로 기준을 적었다는 데 있다. "잘 되는지 봐줘"가 아니라 "11개 나오는지", "상세가 나오는지", "409로 거절되는지"처럼 정답이 정해진 질문을 던진다. 그리고 이 셋은 새로 지어낸 시험이 아니다. "로컬에서 확인했던 것 그대로" — 서버를 처음 만들었을 때 내 컴퓨터에서 확인했던 바로 그 세 가지다. 주소는 한 번만 알려 주고, 어느 경로를 어떻게 호출할지는 명세를 아는 AI가 채운다. 셋을 고른 데에도 뜻이 있다.

  • 공연 목록이 11개 — 목록 조회와 DB 연결이 함께 확인된다. 판매종료 하나를 뺀 수다.
  • 공연 하나의 상세 — 개별 조회가 정확히 되는지 본다.
  • 남은 수량보다 많이 주문하면 409 — 비즈니스 규칙(초과 판매 방지) 이 배포 후에도 살아 있는지 본다. 참고로 409는 "요청이 현재 상태와 충돌한다"는 뜻의 응답 코드로, "남은 좌석보다 많이 주문했다"를 거절할 때 서버가 돌려주는 신호다.

'curl로 실제 호출한 결과를 보여줘'라고 명시한 것도 좋다. AI의 "확인했습니다"라는 말이 아니라 실제 호출의 원문 결과를 요구해, 검증을 증거 기반으로 만든다.

약한 지시 → 강한 지시

강한 지시는 조건을 많이 적은 지시가 아니다. 사람만 아는 결정(어디까지가 내 몫인지, 무엇이 나오면 통과인지)을 말하고, 나머지는 AI가 읽을 기준(설정 파일·명세·로컬에서 했던 확인)에 맡기는 지시다.

흔한(약한) 지시 고친(강한) 지시 무엇을 바꿨나
어떻게 배포하는지 알려줘 api 서버 배포해줘 절차를 물어보지 않고 맡겼다 — 설정 파일이 저장소에 있으니 AI가 읽고 명령을 고른다
시크릿 올려줘 프로덕션에 필요한 시크릿 목록과 그것을 올리는 명령을 알려줘. 값 입력은 내가 직접 한다 사람만 내리는 결정 — 값은 사람이 직접 입력한다. 목록은 AI가 설정과 코드를 읽고 뽑는다
로그인해줘 (지시가 아니라 사람의 일) 터미널에서 wrangler login을 치고 브라우저 승인을 직접 누른다 권한 승인은 사람 몫 — AI에게 넘기지 않는다
잘 됐는지 봐줘 방금 배포한 주소로, 로컬에서 확인했던 것 그대로 — 11개 목록, 공연 상세, 초과 주문 409 — curl로 호출한 결과를 보여줘 기준을 지목했다(로컬에서 통과한 그 세 가지). 눈으로 확인 가능한 사실로
배포 완료됐지? 로컬 서버를 끈 상태에서 배포 주소의 공연 목록 조회가 여전히 응답하는지 확인하자 '됐다는 말' 대신 결정적 증명을 요구

두 가지 실전 감각을 덧붙인다.

  • 점검 보고를 읽고 넘어간다. 배포 지시 앞에 점검을 붙여 두었으니 AI가 항목별 보고를 먼저 내놓는다. 그 보고를 읽지 않고 배포 결과만 보면 점검을 붙인 의미가 없다.
  • 에러가 나면 "원인부터 설명하고"를 붙인다. 배포는 로컬과 환경이 달라 처음엔 종종 실패한다. "배포가 실패했어. 로그를 보고 원인부터 설명한 다음 고쳐줘"라고 하면, AI가 무턱대고 재시도하는 대신 무엇이 왜 막혔는지 먼저 말하게 된다. 흔한 원인은 시크릿 누락, 설정 오류, CI 미통과다.

[짚고 가기] 실습에서 배포가 한 번에 성공하지 않는 경우가 흔하다. 이때 "실패는 정상이고, 실패 로그를 읽는 게 배포의 절반"이라고 생각하면 위축되지 않는다. 가장 흔한 실패는 시크릿을 안 올린 채 배포한 경우 — 서버는 떴는데 공연 목록 조회가 DB 에러를 뱉는다. "떴는데 데이터가 없다 = 시크릿을 의심"이라는 진단 공식을 알아 두면, 스스로 원인을 좁혀 갈 수 있다. 같은 공식이 결제에도 통한다 — 목록은 나오는데 결제 승인만 실패하면 토스 시크릿 키가 등록되지 않은 것이다.

19.5 실습 — API 서버를 배포한다

따라하기는 하나다. 그 안에서 다섯 단계를 차례로 밟는다 — 로그인 → 시크릿 등록 → 남은 변경 올리기 → 배포 → 확인. 로그인과 시크릿 등록은 사람이 터미널에서 직접 하고, 커밋과 배포는 프롬프트로 시키고, push와 마지막 확인은 사람이 한다. 각 단계가 끝날 때마다 결과를 확인한 뒤 다음 단계로 넘어가자.

따라하기 1 — 로그인부터 배포 확인까지

① Cloudflare에 로그인한다.

터미널
$ cd api
$ wrangler login

브라우저가 열리면 Cloudflare 계정으로 로그인하고 "이 도구가 내 계정에 접근하는 것을 허용" 버튼을 누른다. 권한을 넘기는 일이라 사람의 손으로 한다 — 맨 처음 Claude Code에 로그인하던 것과 똑같은 흐름이다. Cloudflare 계정이 아직 없다면 이 단계에서 무료로 하나 만든다(이메일 가입이면 충분하다).

② 프로덕션 시크릿 둘을 등록한다.

터미널
$ wrangler secret put DATABASE_URL
$ wrangler secret put TOSS_SECRET_KEY

둘째 줄의 이름은 예시다. 토스 시크릿 키의 환경변수 이름은 결제를 붙일 때 AI가 붙였으므로, api/.env.example에 적힌 이름 그대로 바꿔 넣는다. 이름이 한 글자라도 다르면 코드는 그 값을 찾지 못한다.

명령을 하나 실행할 때마다 값을 입력하라는 프롬프트가 뜬다. 첫째에는 로컬 .env에 적어 둔 것과 같은 DATABASE_URL(Supabase 연결 문자열, postgresql://... 로 시작하고 중간에 비밀번호가 들어 있다)을, 둘째에는 api/.env에 넣어 둔 것과 같은 토스 시크릿 키(test_sk_...)를 붙여넣는다. 클라이언트 키(test_ck_...)는 여기 넣지 않는다 — 그것은 화면 쪽 값이라 프론트엔드를 배포할 때 다룬다.

이 값은 AI에게 채팅으로 넘기지 않는다. wrangler secret put이 띄운 터미널 입력 프롬프트에 사람이 직접 붙여넣는다. 붙여넣은 값은 화면에 그대로 찍히지 않고, 입력이 끝나면 "시크릿이 저장됐다"는 메시지만 남는다. 값 자체는 화면 로그에 남지 않는다 — 암호화되어 Workers 시크릿으로 등록됐다는 증거다. 다 등록했으면 wrangler secret list로 시크릿 이름 두 개가 보이는지 확인한다(이름만 보이고 값은 보이지 않는 것이 정상이다).

둘 중 하나라도 빠뜨리면 배포는 되는데 서비스가 반쪽이 된다. DATABASE_URL이 없으면 목록 조회부터 실패하고, 토스 시크릿 키가 없으면 목록은 멀쩡히 나오는데 프로덕션에서 결제 승인만 실패한다.

③ 남은 변경 사항을 원격 저장소에 올린다.

배포에 쓰이는 wrangler.toml 같은 설정 파일이 내 노트북에만 남아 있으면, 저장소만 읽어서는 이 서비스가 어떻게 배포되는지 알 수 없다. 배포 전에 한 번 정리하고 간다.

위 프롬프트를 그대로 복사해 입력하면 된다. 다른 내용으로 바꿔서 해 보고 싶다면 자유롭게 바꿔도 좋다.

AI가 wrangler.toml을 읽고 배포 명령을 고른다. 빌드(코드를 Workers가 실행할 수 있는 형태로 묶는 일)와 업로드(그 결과물을 Cloudflare 서버망에 배치하는 일)가 진행되고, 끝나면 https://onticket-api.<계정>.workers.dev 형태의 배포 URL이 찍힌다.

이 주소를 반드시 사람이 직접 메모해 둔다. 눈에 잘 띄는 곳에 적어 두자 — 프론트엔드가 주문 요청을 보낼 주소이고, 프론트엔드를 배포할 때 프롬프트에 사람이 직접 전달할 입력값이다.

⑤ 실제 주소로 확인하고, 로컬을 끈다.

방금 메모한 배포 URL 뒤에 명세(docs/API-Spec.md)에 적힌 공연 목록 조회 경로를 붙여 브라우저 주소창에 연다. 11개 공연이 JSON으로 주르륵 나오면 두 가지가 한꺼번에 증명된다 — 배포된 서버가 응답하고, 시크릿으로 등록한 DATABASE_URL로 DB에도 연결됐다. 주소창을 다시 보자. localhost가 아니라 ...workers.dev다. 이 데이터는 내 노트북 대신 Cloudflare에 배포된 서버가 보내 준 것이다.

이제 로컬 api 서버를 끈다(터미널에서 Ctrl + C). 그 상태로 배포 URL을 새로고침해도 여전히 11개가 나온다 — 내 노트북과 무관하게 서비스가 동작한다는 뜻이고, 이것이 배포의 결정적 증명이다.

[짚고 가기] 이 순간을 그냥 지나치지 말고 기억해 두자. "방금 내 노트북에서 서버를 껐는데, 화면에는 데이터가 나온다 — 이게 배포다." 가능하면 다른 사람의 배포 URL을 열어 보면 실감이 배가된다 — 남의 노트북에서 만든 서비스에 내가 접속되는 경험은, 이 과정의 첫머리에서 예고한 "옆자리 사람이 내 URL로 접속"의 축소판이다.

완료 기준 체크리스트

  • wrangler login 이 완료되어 있다
  • 프로덕션 시크릿 둘(DATABASE_URL, 토스 시크릿 키)이 Workers 시크릿으로 등록돼 있다 (코드엔 없다)
  • wrangler.toml을 비롯해 로컬에만 있던 변경이 저장소에 올라가 있다
  • API가 배포되어 공개 URL이 나왔다
  • 배포 URL의 공연 목록 조회에서 11개 공연이 나온다
  • 로컬 서버를 끈 상태에서도 배포 URL이 응답하는 것을 확인했다
  • 배포 URL을 메모해 두었다 (프론트엔드를 배포할 때 입력값으로 쓴다)

이 일곱 줄은 "배포했다"가 아니라 "배포가 됐다"를 확인하는 항목들이다. 특히 여섯째 줄(로컬을 끈 상태에서도 응답)이 나머지를 대표하는 결정적 증명이다. 하나라도 체크가 안 되면 그 단계로 돌아가 원인을 좁힌다 — 공개 URL이 안 나왔으면 배포를, 데이터가 안 나오면 시크릿 등록을 의심한다. 토스 시크릿 키는 이 장의 확인(11개 목록)으로는 드러나지 않는다 — 결제를 실제로 진행할 때 확인할 수 있으므로, 지금은 등록된 시크릿 이름 두 개를 눈으로 확인해 둔다.

19.6 정리

  • 배포는 코드를 인터넷에 연결된 서버에서 실행해, 24시간 누구에게나 응답하게 하는 일이다. 로컬의 실수는 나만 보지만 배포의 실수는 고객이 본다 — 되돌릴 수 있게, 확인하며 한다.
  • 분리형에서는 API 서버를 먼저 배포한다. 프론트엔드가 요청을 보낼 주소가 있어야 하기 때문이다.
  • Cloudflare Workers — 서버리스, 엣지, 잠들지 않음, 무료 한도. 시크릿은 .env가 아니라 Workers 시크릿(wrangler secret)으로 등록한다. 온티켓은 DATABASE_URL과 토스 시크릿 키 둘이다. 같은 이름의 값이 로컬과 프로덕션에서 각각 다른 곳에서 공급되며, 코드는 값의 출처를 알 필요가 없다.
  • 배포는 명령 한 번이 아니라 배포 전 점검(CI 통과·시크릿·설정) + 배포 후 검증(실제 주소 호출) 의 절차다. "배포했다"와 "배포가 됐다"는 다르다.
  • 로컬을 꺼도 응답하는 것 — 그것이 배포의 증명이다. 사람의 일은 로그인· 시크릿·검증, 나머지는 프롬프트로.

이 장에서 온티켓은 처음으로 내 노트북 밖에 배포됐다. 지금까지의 실습은 전부 localhost에서 진행했지만, 이제 API는 공개 주소를 통해 누구나 호출할 수 있다. 다음에는 이 API에 연결할 프론트엔드를 배포해, 고객이 화면에서 직접 예매할 수 있게 만든다.
