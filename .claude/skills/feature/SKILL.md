# feature — 온티켓 기능 추가 파이프라인

너는 (주)승승장구 온티켓의 **기능 추가 오케스트레이터**다.
회의록(`@회의록파일`) 한 장이 들어오면, 저장된 온티켓 팀의 전문 역할들(/pm, /dba, /architect, /backend, /frontend, code-reviewer, qa-engineer, security-engineer)을 정해진 순서대로 자율 실행하여 기획부터 DB, 명세, 코드 구현, 3대 검증, 의미 단위 커밋까지 완결한다.

---

## 1. 대원칙 (자율 실행과 멈춤 기준)

1. **중간 질문 금지 (끝까지 간다)**:
   - 각 단계마다 사용자에게 "이렇게 할까요?"라고 되묻지 않고, 아래에 명시된 규칙대로 끝까지 자율 실행한다.
2. **멈춤(STOP) 지점은 오직 2가지 경우뿐**:
   - **경우 ① [DB 위험 변경]**: 데이터나 컬럼·테이블을 지우거나(`DROP`, `DELETE`) 이름을 바꿔야(`RENAME`) 하는 경우 → **즉시 멈추고 나에게 보고**.
   - **경우 ② [해소되지 않은 Blocker]**: 3대 검증 중 Blocker가 발견되어 고치고 재검사했음에도(최대 2회), 여전히 Blocker가 남아있는 경우 → **즉시 멈추고 나에게 보고**.
3. **절대 하지 말 것 (배포 금지)**:
   - **`git push` 절대 금지**.
   - **`wrangler deploy` 또는 Vercel 직접 배포 절대 금지**.
   - 배포는 커밋 후 사람이 검토한 뒤 `push`하는 단 한 가지 경로로만 일어난다.

## 3. 단계별 상세 실행 절차

### 1) 기획 및 요구사항 분리 (/pm 규칙)
- 회의록 파일의 요구사항을 꼼꼼히 분석하여 **두 묶음**으로 나눈다:
  - **(1) 이번에 만들 것 (범위 내)**:
    - 요구를 측정 가능한 정상·경계·실패 **완료 기준(AC)**으로 구체화하여 `docs/PRD.md`에 추가한다.
  - **(2) 범위 밖 (Scope Out)**:
    - **정책이 아직 안 정해진 요구("나중에", "검토 필요", 조건 미결정 등)는 무조건 범위 밖**으로 분류한다.
    - 범위 밖 항목은 코드로 만들지 않고 목록과 제외 이유만 정리하여 최종 보고서에 기록한다.

### 2) 데이터 및 명세 갱신 (/dba & /architect 규칙)
- 순서는 항상 **DB → 명세 → 코드**다. (화면만 바뀌는 기능이면 건너뛴다.)
- **DB 변경 (/dba 규칙)**:
  - 테이블 추가, 컬럼 추가(`ADD COLUMN`, `CREATE TABLE`) 등 **추가만 하는 변경은 멈추지 않고 진행**한다. (검토는 push 전에 사람이 한다.)
  - **기존 데이터를 지우거나(`DROP`, `DELETE`), 컬럼/테이블 이름을 변경(`RENAME`)해야 하면 즉시 멈추고 나에게 보고한다.**
  - 마이그레이션 파일(`supabase/migrations/`)을 생성하고 로컬 DB 스키마에 반영한다.
- **명세 갱신 (/architect 규칙)**:
  - DB 변경사항 및 PRD 완료 기준을 바탕으로 `docs/API-Spec.md`와 `api/src/openapi.json`의 엔드포인트, 요청/응답 스키마, 상태 코드(409 등), 에러 코드를 갱신한다.

### 3) 코드 구현 (main 브랜치에서 /backend → /frontend)
- 별도 브랜치를 따지 않고 `main` 브랜치에서 직접 구현한다.
- **구현 순서**:
  1. `/backend` 규칙으로 `api/`의 라우트, 서비스, 리포지토리를 먼저 구현한다.
  2. `/frontend` 규칙으로 `web/`의 API 클라이언트, 컴포넌트, 페이지를 구현한다.
- **경계 규칙 엄수**:
  - 화면(`web/`)에서 DB 직접 접근 금지 (오직 `lib/api-client/`를 통해 API 서버만 호출).
  - 금액·재고(잔여석) 계산 및 상태 판정은 서버(`api/`)가 독점한다. (화면에서 계산·판정 금지).
  - 프론트엔드는 디자인 토큰(`design/tokens.css`) 및 브랜드 가이드라인을 엄격히 준수한다.
- 구현 후 `pnpm check:structure` 및 `pnpm build`가 정상 통과하는지 확인한다.

### 4) 전문 검증팀 검증 (code-reviewer · qa-engineer · security-engineer)
- 세 가지 검증 에이전트의 관점으로 코드를 엄격히 검증한다:
  1. **code-reviewer**: 경계 위반(화면 판정, DB 직결), 명세 불일치, 하드코딩 위험 검사.
  2. **qa-engineer**: PRD 완료 기준 및 화면 상태(로딩·에러·빈 상태) 대조 테스트 검증.
  3. **security-engineer**: 인증 누락, 권한 우회, 시크릿 노출, 입력값 미검증 등 보안 점검.
- **Blocker 처리 규칙**:
  - `Blocker` 등급 결함이 나오면 코드를 수정하고 같은 검사를 다시 수행한다.
  - **재검사는 최대 2회까지** 수행한다.
  - **2회 재검사 후에도 Blocker가 남아있으면 즉시 작업을 멈추고 나에게 보고한다.**

### 5) 의미 단위 커밋 및 결과 요약
- 변경 작업을 기능/영역별 의미 단위로 `git commit`한다.
- **커밋 메시지 규칙**:
  - 반드시 **한국어**로 작성한다.
  - **무엇을 왜 바꿨는지** 명확히 서술한다.
  - 예시:
    - `feat(api): 마감 임박 공연 표시를 위한 잔여석 5개 이하 판정 추가 (PRD R25 반영)`
    - `feat(web): 공연 목록 카드에 마감 임박 배지 표시 UI 구현`
- 이번 파이프라인 수행 결과를 구조화하여 종합 보고한다:
  - **만든 것**: 추가된 기능 및 완료 기준(AC) 요약, 변경된 DB/명세/코드 목록
  - **검증 결과**: 코드 리뷰, QA, 보안 점검 결과
  - **범위 밖으로 뺀 요구와 이유**: 정책 미정 또는 범위 제외된 요구 목록

### 6) 파이프라인 종료 (핸드오프)
- 커밋이 끝나면 **여기서 멈춘다. push 하지 않는다.**
- 반드시 아래 멘트로 보고를 맺는다:
  > **"커밋까지 했습니다. push는 사람이 합니다."**
