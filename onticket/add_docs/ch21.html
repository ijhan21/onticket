21장. 배포 자동화 — push하면 자동으로 배포된다

이 장이 끝나면: main에 push하는 것만으로 온티켓이 저절로 배포된다. 저장소 하나에 web/과 api/가 함께 있는 모노레포라, 경로 필터로 바뀐 폴더에 해당하는 배포만 돌게 갈라 둔다. 배포 토큰을 저장소 시크릿으로 등록하고, 작은 변경 하나를 push해 한쪽 배포만 도는 것을 눈으로 확인한다.

21.1 개념 — 수동 배포의 한계

손으로 배포하면 무엇이 어긋나나

앞 장까지 온티켓의 API와 프론트엔드를 배포했다. api는 Cloudflare Workers에, web은 Vercel에 배포하고, CORS를 설정해 공개 주소에서 예매 과정 전체를 확인했다. 현재 서비스는 사람이 배포를 지시해 반영한 상태다.

문제는 그다음부터다. 코드는 계속 바뀐다. 버그를 고치고, 문구를 다듬고, 기능을 얹는다. 고친 코드를 커밋하고, main에 push하고, 검사가 초록이 된다. 여기까지는 자동으로 흘러간다. 그런데 배포 명령을 치는 것은 여전히 사람이다. 치는 것을 깜빡하면 어떻게 되는가.

저장소의 코드와 배포된 코드가 달라진다. 저장소에는 고쳐진 코드가 있는데, 고객이 보는 화면은 옛날 것이다. "내 노트북에선 고쳤는데요"가 아니라 "저장소에는 고쳐져 있는데요"가 된다. 더 나쁜 것은 이 어긋남이 아무 신호도 내지 않는다는 점이다. 빨간 X가 뜨지도 않고, 에러가 나지도 않는다. 서비스는 멀쩡히 잘 돈다 — 옛날 코드로. 며칠 뒤 누가 "이거 고친다고 하지 않았어요?"라고 물을 때에야 드러난다.

정리하면, 지금 온티켓에는 사람이 기억해서 실행해야 하는 단계가 하나 남아 있다. 검사는 저장소가 대신 해 주는데, 배포는 아직 사람이 기억해야 한다. 이 장에서는 배포도 자동으로 실행되도록 설정한다.

CD — 배포도 자동이 된다

코드가 올라오면 기계가 검사해 주는 체계를 CI라고 불렀다. 그 짝이 되는 개념이 CD(지속적 배포) 다. CI가 "올라온 코드가 멀쩡한지 검사"라면, CD는 "검사를 통과한 코드를 자동으로 배포하는 것" 이다. 사람이 배포 명령을 치는 대신, 정해진 사건(우리 경우 main에 push)이 일어나면 배포 작업도 자동으로 실행된다.

CI를 세울 때 익힌 문법이 그대로 쓰인다. 검사를 돌리던 GitHub Actions에게 "검사 말고 배포도 해라"를 시키는 것뿐이다. 새로 배울 도구는 없다. 새로 정할 것은 언제 도는지와 무엇이 바뀌면 무엇을 배포하는지 둘뿐이다.

왜 모노레포에서는 앱별로 배포해야 하는가

여기서는 온티켓의 저장소 구조를 고려해야 한다. 뼈대를 세울 때 우리는 저장소 하나에 web/과 api/를 함께 담는 모노레포를 골랐다. 그런데 이 두 앱은 배포처가 다르다. web은 Vercel로, api는 Cloudflare Workers로 간다.

그래서 "main에 push하면 배포한다"를 아무 조건 없이 걸면 이렇게 된다.

  • api/의 버그 하나를 고쳐 push했다 → 프론트까지 다시 배포된다.
  • 화면 문구 한 줄을 고쳐 push했다 → API 서버까지 다시 배포된다.

건드리지도 않은 쪽을 다시 올릴 이유가 없다. 쓸데없이 시간이 들고, 불필요한 배포가 실패할 가능성도 생기고, 무엇보다 배포 기록이 지저분해진다. 나중에 "API가 언제부터 이상해졌지?"를 되짚을 때, 손도 안 댄 날짜의 배포 기록이 잔뜩 섞여 있으면 추적이 어려워진다.

답은 경로 필터(path filter) 다. "어떤 폴더의 파일이 바뀐 커밋에만 이 배포를 돌린다"를 워크플로에 적는 것이다.

api/ 가 바뀐 push  →  Cloudflare Workers 배포만 돈다
web/ 이 바뀐 push  →  Vercel 배포만 돈다
둘 다 바뀐 push    →  둘 다 돈다
문서만 바뀐 push   →  아무것도 안 돈다

이것이 이 장의 알맹이다. 모노레포에서 자동 배포를 세운다는 것은 사실상 "무엇이 바뀌면 무엇을 배포하는가"를 저장소에 적어 두는 일이다.

왜 GitHub Actions 하나로 통일하나

Vercel에는 저장소를 지켜보다가 알아서 배포해 주는 Git 연동 기능이 있다. 그걸 켜면 web 쪽은 워크플로를 쓰지 않아도 된다. 그런데 이 장에서는 두 배포를 모두 GitHub Actions로 세운다. 이유는 셋이다.

  • 한 곳에서 보인다. 모노레포에서 가장 중요한 정보는 "무엇이 바뀌면 무엇이 배포되는가"다. 두 배포가 모두 저장소의 워크플로 파일에 적혀 있으면, 그 파일을 열어 눈으로 읽을 수 있다.
  • 설정이 갈리지 않는다. Vercel Git 연동을 쓰면 "이 저장소의 루트가 아니라 web 폴더를 배포하라"는 설정이 Vercel 대시보드 안에 따로 숨는다. 저장소를 아무리 읽어도 그 설정은 안 보인다. 배포 규칙이 저장소와 대시보드 두 군데로 나뉘는 것이다. 설정 파일을 기준으로 삼는다는 원칙이 여기서도 그대로 적용된다.
  • 이미 아는 문법이다. CI 워크플로를 만들고 한 줄씩 읽어 봤으니, 같은 on·jobs·steps 구조를 그대로 쓴다. 새 개념은 경로 필터 하나뿐이다.

자동 배포는 누가 결정하는가

여기서 한 번 멈추자. "배포 명령을 직접 실행하지 않아도 서비스에 반영된다"는 말은 불안하게 들린다. 잘못된 코드가 저절로 고객에게 간다는 뜻 아닌가?

아니다. 무엇을 배포할지 결정하는 것은 여전히 사람이다. 자동화된 것은 결정이 아니라, 결정한 뒤에 따라오는 노동이다. 순서를 늘어놓으면 분명해진다.

단계 누가 하나 무엇인가
코드를 고친다 사람이 AI에게 시킨다 변경
커밋한다 사람이 AI에게 시킨다 변경을 의미 단위로 묶어 기록
"푸시해줘"라고 시킨다 사람 "이 변경을 배포한다"는 결정
검사가 돈다 기계(CI) 멀쩡한지 판정
배포가 돈다 기계(CD) 결정을 실행

자동화를 걸고 나면 push가 곧 배포 버튼이 된다. 그러니 "자동으로 배포된다"는 말은 "아무나 아무거나 올릴 수 있다"가 아니다. 버전 관리 규칙에 적어 둔 대로 AI는 커밋까지 하고, push는 사람이 "푸시해줘"라고 할 때만 한다. 사람이 배포하기로 결정한 변경만 반영된다. 자동화는 그 결정 이후의 작업을 대신한다.

오히려 손으로 배포할 때가 더 위험하다. 손으로 하면 "검사를 안 거친 코드를 급하게 올리는" 지름길이 늘 열려 있다. push에 배포를 묶어 두면 그 지름길이 막힌다.

[짚고 가기] "자동 배포 = 사람이 판단을 놓는 것"이라는 오해를 여기서 풀어 두자. 이 과정 전체를 관통하는 한 문장이 여기서도 같다 — AI와 자동화는 결정을 대신하지 않고, 결정한 뒤의 작업을 대신한다. "푸시해줘"라고 시키는 사람이 배포를 결정한다는 것을 학생이 말로 설명할 수 있으면 이 절은 성공이다.

21.2 용어 정리

CD (지속적 배포, Continuous Deployment)

CD는 저장소에 올라온 코드가 사람의 배포 명령 없이 자동으로 배포되는 방식이다. 'Continuous Deployment'의 머리글자이고 '지속적 배포'로 옮긴다. CI와 짝을 이룬다.

약어 한국어 하는 일 온티켓에서
CI 지속적 통합 올라온 코드가 멀쩡한지 검사한다 빌드·타입 검사 워크플로
CD 지속적 배포 검사를 통과한 코드를 자동으로 배포한다 이 장에서 만드는 배포 워크플로

'지속적(Continuous)'이라는 말이 왜 붙었는지도 짚어 두자. 예전에는 몇 달 치 변경을 모아 두었다가 한꺼번에 내보냈다. 그러면 문제가 생겼을 때 의심할 후보가 수백 개다. 어느 변경이 범인인지 찾는 데만 며칠이 간다. 반대로 작게 자주 내보내면, 문제가 생겨도 방금 바꾼 작은 조각 하나만 의심하면 된다. 되돌리기도 쉽다. "작게, 자주, 끊김 없이"가 '지속적'에 담긴 뜻이고, 자동화는 그것을 가능하게 하는 장치다. 배포가 번거로우면 사람은 자연히 모아서 한다.

경로 필터 (path filter)

경로 필터는 "어떤 파일이 바뀐 커밋에만 이 작업을 돌린다"를 적는 장치다. 워크플로의 트리거에 paths: 항목으로 적는다. 모노레포 자동화의 핵심 장치가 바로 이것이다.

앱이 하나뿐인 저장소라면 필요 없다. 무엇이 바뀌든 배포할 것은 하나니까. 온티켓처럼 저장소 하나에 배포처가 다른 앱이 둘 있을 때, 경로 필터가 "이번 push는 누구 일인가"를 가른다.

읽기용으로 뼈대를 하나 보자. api 배포를 맡는 워크플로의 골격이다.

# 읽기용 예시 — 구조만 본다
name: Deploy API
on:
  push:
    branches: [main]      # main에 들어온 변경일 때
    paths:                #  그중에서도 이 경로가 바뀐 경우에만
      - 'api/**'
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - 코드 받기
      - 의존성 설치
      - 배포 (저장소 시크릿에 등록한 토큰으로 인증)

소리 내어 읽으면 이렇다 — "main에 push된 변경 중에서 api/ 아래 파일이 바뀐 경우에만, 리눅스 머신에서, 코드를 받아 설치하고 배포한다." api/**에서 **는 "그 폴더 아래 모든 것"을 뜻하는 표시다. web 쪽은 이 뼈대에서 paths:가 web/**로, 배포 스텝이 Vercel용으로 바뀐 것이 붙는다.

이 예시에서 확인할 것은 워크플로의 구조다. on(언제) 아래에 branches(어느 브랜치)와 paths(어느 폴더)가 함께 놓인다는 것, jobs 아래에 배포 잡이 있다는 것 — 여기까지가 우리가 읽어 낼 몫이다. 실제 스텝에 들어갈 액션 이름과 버전, 정확한 배포 명령은 적지 않았다. 그것은 AI가 프로젝트를 보고 채운다. 우리는 채워진 파일을 읽는다. 두 배포를 파일 하나에 담을지 둘로 나눌지도 마찬가지로 AI가 정하게 두고, 우리는 "무엇이 바뀌면 무엇이 배포되는가"가 그 파일에서 눈에 보이는가만 확인한다.

배포 토큰

여기서 새 문제가 하나 생긴다. api를 손으로 배포할 때 우리는 터미널에서 wrangler login을 쳤고, 브라우저가 열렸고, 사람이 "허용" 버튼을 눌렀다. 클라우드 머신에서는 그렇게 할 수 없다. 배포를 돌리는 리눅스 머신에는 브라우저도 없고, 버튼을 누를 사람도 없다.

그래서 기계에게는 다른 인증 수단을 준다. 배포 토큰이다. 토큰은 사람의 로그인 대신 기계가 "나는 이 계정의 권한을 위임받았다"를 증명하는 긴 문자열이다. 사람은 브라우저에서 로그인하고, 자동 배포 작업은 토큰으로 인증한다고 보면 된다.

사람이 배포할 때 기계가 배포할 때
인증 수단 브라우저 로그인 배포 토큰
어디서 얻나 계정으로 로그인 각 서비스 대시보드에서 발급
어디에 두나 내 컴퓨터에 남는 로그인 상태 저장소 시크릿

토큰은 비밀 값이다. 코드에 적어 저장소에 올리면 그걸 주운 누구나 우리 계정으로 배포할 수 있게 된다. 그래서 GitHub이 제공하는 저장소 시크릿에 등록한다. 시크릿으로 등록하면 워크플로는 이름으로 그 값을 꺼내 쓸 수 있고, 사람은 등록한 뒤 다시 꺼내 볼 수 없다. api 시크릿을 Workers 시크릿으로 올릴 때 겪은 성질 그대로다 — 이름은 보이고 값은 안 보인다.

온티켓은 배포처가 둘이라 토큰도 두 갈래다. Cloudflare 쪽은 API 토큰 하나, Vercel 쪽은 토큰에 더해 어느 조직·어느 프로젝트로 배포할지 가리키는 식별자가 함께 필요하다. 정확히 몇 개를, 어떤 이름으로 등록해야 하는지는 AI가 만든 워크플로 파일에 적혀 있다. 쓰는 액션과 버전에 따라 이름이 다르므로, 외워서 적지 말고 파일에 적힌 이름을 그대로 쓴다. 그래서 이 장의 프롬프트 마지막 줄이 "다 만들면 필요한 시크릿 이름을 알려줘"다.

[짚고 가기] 시크릿이 세 군데로 늘어난 것이 헷갈릴 수 있다. 정리하면 이렇다 — Workers 시크릿은 배포된 API가 돌아가는 데 쓰는 값(DB 주소·결제 키), Vercel 환경변수는 화면이 쓰는 공개 값, 저장소 시크릿은 배포하는 행위 자체에 필요한 값(토큰)이다. "서비스가 쓰는 값"과 "배포가 쓰는 값"은 다르며, 등록하는 곳도 다르다. 이 구분을 말로 할 수 있으면 충분하다.

21.3 프롬프트 작성법 — 앱별 배포를 요청한다

배포 자동화에서도 원칙은 같다. 사람만 아는 결정을 말하고, 나머지는 AI가 읽을 기준을 가리킨다. 이번에 사람만 아는 결정은 셋이다.

  • 언제 도는가 — main에 push할 때. "매일 밤"도 아니고 "사람이 손으로 명령을 칠 때"도 아니다. 이건 코드를 읽어서는 알 수 없는, 우리 팀의 운영 방침이다.
  • 무엇이 바뀌면 무엇을 배포하는가 — api/면 Workers, web/이면 Vercel. 모노레포의 두 폴더를 어디로 보낼지는 사람이 정한 구조다.
  • 어디까지가 AI의 몫인가 — 파일까지 만들고, 시크릿 이름을 알려 주는 데까지. 토큰 값은 사람이 직접 입력한다.

반대로 AI가 채우는 것은 이렇다. 스텝의 순서, 가져다 쓸 액션의 이름과 버전, 정확한 배포 명령, 시크릿을 읽어 오는 문법, 파일을 몇 개로 나눌지. 이것들은 프로젝트 설정과 도구의 사정에 달린 문제라 사람이 불러 줄 수 없다.

이 나눔을 그대로 문장으로 옮기면 프롬프트가 된다.

프롬프트
main에 push하면 자동으로 배포되게 해줘. 모노레포니까 api/ 가 바뀌면 Cloudflare Workers에,web/ 이 바뀌면 Vercel에, 변경된 앱만 배포되게 분리해줘.프로젝트 구조를 먼저 확인해서 맞추고, 다 만들면 필요한 시크릿 이름을 알려줘.

세 줄이 각각 하나씩 맡고 있다. 첫 줄이 언제, 둘째 줄이 무엇이 바뀌면 무엇을, 셋째 줄이 어디까지다. "변경된 앱만"이라는 표현이 경로 필터를 요구하는 대목이고, 이 말을 빼면 AI는 친절하게 둘 다 배포하는 워크플로를 만들어 온다.

적지 않은 것도 많다. 적지 않아도 되는 이유와, 대신 사람이 어디서 확인하는지를 표로 정리하면 이렇다.

프롬프트에 적지 않은 것 왜 안 적어도 되는가 사람은 어디서 확인하나
파일 위치(.github/workflows/ 아래) GitHub이 정한 규칙이라 AI가 안다 만들어진 파일의 경로를 눈으로 본다
경로 필터를 적는 문법(paths:와 **) YAML과 Actions의 문법이다. AI가 안다 파일에서 paths: 두 줄을 찾아 읽는다
배포에 쓸 액션의 이름과 버전 도구마다 정해져 있고 버전이 계속 바뀐다. AI가 맞춘다 파일의 해당 줄이 무슨 일을 하는지 설명을 듣는다
정확한 배포 명령과 빌드 스텝 프로젝트 설정 파일에 적혀 있다. "프로젝트 구조를 먼저 확인해서"가 이 나열을 대신한다 만들어진 파일을 한 줄씩 읽는다
시크릿을 읽어 오는 문법 Actions의 정해진 표기법이다 시크릿 이름만 확인하고, 그 이름으로 등록한다

마지막 줄이 이 장에서 특히 중요하다. 시크릿 이름을 미리 정하지 않는 이유는, 선택한 액션과 워크플로에서 사용하는 이름에 맞춰 등록해야 하기 때문이다. 그래서 순서가 거꾸로다 — 사람이 이름을 정해 주는 것이 아니라, AI가 파일을 만들고 나서 필요한 이름을 알려 주면 사람이 그 이름으로 등록한다. 프롬프트 마지막 줄이 그 순서를 만든다.

약한 지시 → 강한 지시

강한 지시는 조건을 많이 적은 지시가 아니다. 사람만 아는 결정을 말하고, 나머지는 AI가 읽을 기준(여기서는 프로젝트 구조)을 지목하는 지시다.

흔한(약한) 지시 고친(강한) 지시 무엇을 바꿨나
배포 자동화 해줘 main에 push하면 자동으로 배포되게 해줘 '자동'을 구체적 사건으로 — 언제 도는지는 사람의 결정이다
두 앱 다 배포되게 해줘 모노레포니까 api/ 가 바뀌면 Cloudflare Workers에, web/ 이 바뀌면 Vercel에, 변경된 앱만 배포되게 분리해줘 모노레포라는 사정과 폴더별 배포처 — 구조를 정한 사람만 아는 것을 말했다
워크플로 파일 잘 만들어줘 프로젝트 구조를 먼저 확인해서 맞추고 스텝을 불러 주는 대신, AI가 읽을 기준(저장소의 실제 구조)을 지목
시크릿은 CLOUDFLARE_TOKEN으로 해줘 다 만들면 필요한 시크릿 이름을 알려줘 이름을 사람이 지어내지 않는다 — 액션에 필요한 이름을 AI가 알려 주게 했다
토큰 값 넣어 줄 테니 등록까지 해줘 (지시가 아니라 사람의 일) 터미널에서 사람이 직접 등록한다 비밀 값을 대화창에 남기지 않는다

실전 감각을 둘 덧붙인다.

  • 만든 파일을 설명하게 시킨다. CI 워크플로를 만들 때처럼 "이 파일을 한 줄씩 풀어 줘"를 덧붙이면, 읽어서 확인하는 일이 쉬워진다. 특히 paths:가 어떻게 갈렸는지는 반드시 설명을 듣고 넘어간다.
  • 실패하면 로그 원문을 준다. 첫 자동 배포는 자주 실패한다. 대개 코드가 아니라 토큰이나 설정 문제다. Actions 로그의 빨간 스텝을 펼쳐 마지막 몇 줄을 그대로 주고 "이 로그를 보고 원인부터 설명한 다음 고쳐줘"라고 시킨다.

21.4 실습 — push할 때 자동으로 배포한다

따라하기는 하나다. 그 안에서 세 단계를 밟는다 — 워크플로 생성·읽기·올리기 → 토큰을 저장소 시크릿으로 등록 → 작은 변경 하나로 확인. 만드는 일은 프롬프트로 시키고, 시크릿 등록은 사람이 터미널에서 직접 하고, push는 사람이 정할 때 시키고, 마지막은 사람이 눈으로 확인한다.

준비물은 앞에서 다 갖췄다. 두 앱이 각자 공개 주소로 떠 있어야 하고, 저장소에 CI 워크플로가 있어야 하고, gh에 로그인돼 있어야 한다.

따라하기 1 — push할 때 배포되도록 설정한다

① 워크플로를 만들고, 경로가 어떻게 갈렸는지 읽고, 저장소에 올린다.

프롬프트
main에 push하면 자동으로 배포되게 해줘. 모노레포니까 api/ 가 바뀌면 Cloudflare Workers에,web/ 이 바뀌면 Vercel에, 변경된 앱만 배포되게 분리해줘.프로젝트 구조를 먼저 확인해서 맞추고, 다 만들면 필요한 시크릿 이름을 알려줘.

위 프롬프트를 그대로 복사해 입력하면 된다. 다른 내용으로 바꿔서 해 보고 싶다면 자유롭게 바꿔도 좋다.

만들어진 워크플로 파일을 연다. .github/workflows/ 아래에 있고, 앞에서 만든 CI 파일 옆에 나란히 놓인다. CI 파일을 읽었던 것과 똑같은 방식으로 읽는다.

읽을 때 찾을 것은 셋이다.

찾을 것 어디를 보나 무엇을 확인하나
언제 도는가 on: 아래 main에 push할 때로 되어 있나
무엇이 바뀌면 도는가 paths: 아래 한쪽은 api/, 다른 쪽은 web/로 갈렸나
무엇을 하는가 jobs: 아래 steps: 코드 받기 → 설치 → 배포 순서가 보이나

가운데 줄이 이 장의 핵심이다. paths:에 적힌 경로를 소리 내어 읽어 보자 — "api 폴더의 파일이 바뀌면 API를 배포한다", "web 폴더의 파일이 바뀌면 프론트엔드를 배포한다". 이 두 줄이 모노레포에서 두 배포를 가르는 전부다.

액션 이름이나 버전이 이 교재의 예시와 글자까지 같을 필요는 없다. 프로젝트와 도구 사정에 따라 다르게 나온다. 중요한 것은 그 줄이 무엇을 하는 줄인지 내가 말할 수 있는가다. 모르는 줄이 있으면 "이 줄이 무슨 일을 하는지 설명해줘"라고 물으면 된다. "내가 이 파일을 읽고 설명할 수 있는가" 가 이 단계의 완료 조건이다.

파일을 만든 뒤 AI가 필요한 시크릿 이름 목록을 알려 준다. 그 목록을 메모해 둔다. 다음 단계에서 그대로 쓴다.

읽었으면 파일을 저장소에 올린다. 워크플로는 main에 있는 것이 도는 것이라, 내 노트북에만 있으면 자동으로 실행되지 않는다.

프롬프트
방금 만든 워크플로 커밋해줘.
프롬프트
푸시해줘.

push한 뒤 Actions 탭을 열어 보면 배포는 하나도 안 돈다. 이번 push에서 바뀐 것은 .github/ 아래뿐이라, 경로 필터가 "api도 web도 아니다"라고 판정한 것이다. 방금 읽은 paths: 두 줄이 처음 일한 장면이다.

② 배포 토큰을 저장소 시크릿으로 등록한다.

먼저 토큰을 발급받는다. 이것은 사람이 각 서비스 대시보드에 찾아가서 하는 일이다 — Cloudflare 대시보드에서 API 토큰을, Vercel 대시보드에서 토큰과 프로젝트·조직 식별자를 발급·확인한다. 발급 화면의 위치와 권한 선택지는 서비스 쪽 사정이라 바뀌기도 하니, 헤매면 "Cloudflare에서 배포용 API 토큰을 어디서 어떤 권한으로 발급하는지 알려줘"라고 물어 안내를 받는다.

받은 값은 터미널에서 사람이 직접 등록한다.

터미널
$ gh secret set {워크플로에 적힌 시크릿 이름}

{…} 자리만 실제 이름으로 바꿔 입력한다. 시크릿 이름은 ① 에서 AI가 알려 준 그 이름을 그대로 쓴다. 액션과 버전에 따라 이름이 다르므로, 비슷해 보인다고 고쳐 쓰면 워크플로가 값을 못 찾는다. 이름이 여럿이면 이름 하나당 한 번씩, 여러 번 실행한다.

명령을 실행하면 값을 붙여넣으라는 입력 프롬프트가 뜬다. 이 값은 AI에게 채팅으로 넘기지 않는다. 터미널의 입력 자리에 사람이 직접 붙여넣는다. Workers 시크릿을 올릴 때 지킨 원칙 그대로다 — AI는 명령까지, 비밀은 사람 손으로. 다 끝났으면 gh secret list로 등록된 이름들이 보이는지 확인한다. 이름만 보이고 값은 안 보이는 것이 정상이다.

③ 작은 변경 하나로 확인한다.

이제 진짜로 도는지 본다. 확인 방법은 CI를 세울 때와 같은 발상이다 — 말로 "됐다"를 듣는 대신, 사건을 하나 일으켜 눈으로 본다.

화면 문구 한 줄을 고친다. 홈 화면의 안내 문구처럼 눈에 띄고 되돌리기 쉬운 것이면 된다.

프롬프트
홈 화면 안내 문구 한 줄만 고치고 커밋해줘.
프롬프트
푸시해줘.

push한 직후 GitHub 저장소의 Actions 탭을 연다. 여기서 볼 것이 이 실습의 전부다.

보는 것 통과 신호 무엇을 증명하나
방금 push로 도는 워크플로 배포 워크플로가 실행 중이다 push를 계기로 배포가 시작됐다
api 배포는 도는가 안 돈다(건너뛴다) 경로 필터가 일했다
web 배포 초록으로 끝난다 Vercel 배포가 토큰으로 인증에 성공했다
공개 프론트 주소 잠시 뒤 고친 문구가 보인다 변경 사항이 배포된 서비스에 반영됐다

가운데 두 줄이 이 장의 결론이다. 화면 문구만 고쳤는데 web 배포만 돌고 api는 안 돈다 — 우리가 paths:에 적어 둔 두 줄이 일한 증거다. 반대로 api 쪽 파일을 한 줄 고쳐 push하면 정반대가 된다. 여유가 있으면 한 번 더 해 보면 확실해진다.

마지막 줄도 빠뜨리지 말자. Actions가 초록이라고 끝이 아니다. 앞에서 익힌 "배포했다 ≠ 배포가 됐다"가 여기서도 같다. 공개 주소를 열어 고친 문구가 실제로 보이는지까지 봐야 전체 과정이 마무리된다. 그 문구가 눈에 보이는 순간, 사람이 친 배포 명령은 한 줄도 없었다는 것을 떠올려 보자. 사람이 한 일은 "푸시해줘" 한마디다.

완료 기준 체크리스트

  • 배포 워크플로가 있고, paths:가 api/와 web/로 갈린 것을 읽고 설명할 수 있다
  • 그 워크플로 파일이 저장소의 main에 올라가 있다
  • 배포 토큰이 저장소 시크릿으로 등록돼 있다 (gh secret list에 이름만 보인다)
  • 작은 변경을 push했더니 해당하는 배포만 도는 것을 Actions 탭에서 봤다
  • 공개 주소에서 그 변경이 실제로 반영된 것을 확인했다

[짚고 가기] 첫 자동 배포가 빨간 X로 끝나는 경우가 흔하다. 대개 코드가 아니라 토큰 문제다 — 이름을 다르게 등록했거나, 발급할 때 권한을 좁게 준 경우다. 로그의 빨간 스텝을 펼치면 "인증에 실패했다"는 취지의 메시지가 찍혀 있다. 당황하지 말고 그 몇 줄을 복사해 AI에게 주면 된다. 이 실패를 한 번 겪어 보는 것 자체가 좋은 경험이다 — 기계가 무엇으로 인증하는지를 몸으로 알게 된다.

21.5 정리

  • 손으로 배포하면 저장소의 코드와 배포된 코드가 달라질 수 있다. 이 어긋남은 에러를 내지 않아서 더 위험하다. 서비스는 멀쩡히 잘 돈다 — 옛날 코드로.
  • CD(지속적 배포) 는 CI의 짝이다. CI가 올라온 코드를 검사하는 것이라면, CD는 검사를 통과한 코드를 자동으로 배포하는 것이다. 작게 자주 내보내면 문제가 생겨도 방금 바꾼 작은 조각 하나만 의심하면 된다 — '지속적'에 담긴 뜻이 그것이다.
  • 모노레포에서는 배포를 앱별로 나눠야 한다. 저장소는 하나인데 배포처가 둘이기 때문이다. 나누지 않으면 문구 한 줄을 고쳐도 API 서버까지 다시 올라간다.
  • 앱별 실행 여부를 정하는 설정이 경로 필터다. 워크플로 트리거의 paths:에 "어떤 폴더가 바뀐 커밋에만 돈다"를 적는다. 모노레포 자동 배포를 세운다는 것은 결국 "무엇이 바뀌면 무엇을 배포하는가"를 저장소에 적어 두는 일이다.
  • 두 배포를 모두 GitHub Actions에 두는 이유는 설정이 한 곳에서 보이게 하려는 것이다. 호스팅의 Git 연동을 쓰면 배포 규칙 일부가 대시보드에 숨어, 저장소를 읽어도 안 보인다.
  • 클라우드 머신은 브라우저 로그인을 할 수 없다. 그래서 기계는 배포 토큰으로 인증하고, 그 토큰은 저장소 시크릿으로 등록한다. 등록할 이름은 사람이 지어내지 않는다 — AI가 만든 워크플로 파일에 적힌 이름 그대로 쓴다. 값은 사람이 직접 입력한다.
  • 환경변수와 시크릿을 보관하는 곳은 셋으로 나뉜다 — 서비스가 돌아가는 데 쓰는 값(Workers 시크릿), 화면이 쓰는 공개 값(호스팅 환경변수), 배포하는 행위에 필요한 값(저장소 시크릿).
  • 자동화는 결정을 대신하지 않는다. 어떤 변경을 배포할지는 여전히 사람이 정하고, 그 결정을 실행하는 명령이 push다. 커밋은 AI가, push는 사람이 "푸시해줘"라고 할 때. 자동화가 대신하는 것은 결정한 뒤의 노동이다 — push 한 번이 곧 배포 버튼이다.
  • 워크플로 파일도 저장소에 올라가 있어야 돈다. 내 노트북에만 있는 워크플로는 아무 일도 하지 않는다.
  • 자동화가 도는지는 말이 아니라 사건으로 확인한다. 작은 변경 하나를 push해서, 해당하는 배포만 도는 것과 공개 주소에 반영된 것을 눈으로 본다.

이제 코드를 고치고, 커밋하고, push하면 검사와 배포가 자동으로 실행된다. 다음 장에서는 배포 후 운영을 다룬다. 고객이 예상하지 못한 순서로 서비스를 이용하거나 오류가 발생했을 때, 원인을 어떻게 찾고 대응하는지 알아본다.
