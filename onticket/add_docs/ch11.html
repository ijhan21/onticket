11장. 백엔드 개발자 — API 서버를 맡긴다

이 장을 마치면 백엔드 개발자 스킬로 api/ 안에 공연 목록·상세 조회, 주문 생성, 입장 확인, 내 티켓 조회와 판매 현황 조회 등을 API 명세서대로 구현할 수 있다. 첫 엔드포인트부터 Supabase DB에 연결하고, Swagger UI에서 직접 눌러 보며 응답을 확인한다. 잔여 수량보다 많은 주문이 409로 거절되는지, 정상 주문이 DB에 저장되는지도 확인한다.

11.1 개념 — 백엔드 개발자의 직업윤리는 "명세 그대로"

백엔드가 도대체 무엇인가 — 화면 뒤의 일

'백엔드(backend)'라는 말부터 풀고 시작하자. 우리가 앞에서 만든 것은 사람이 눈으로 보고 손으로 누르는 화면 — 프론트엔드(frontend), 즉 '앞단'이다. 백엔드는 그 화면 뒤에서 데이터를 보관하고, 계산하고, 규칙을 지키는 쪽 — '뒷단'이다. 식당에 비유하면 프론트엔드는 고객이 앉는 홀과 메뉴판이고, 백엔드는 주방이다. 고객은 주방을 직접 보지 못하지만, 실제로 요리가 만들어지고 재고가 관리되는 곳은 주방이다.

온티켓으로 옮기면 이렇다. 관객이 보는 예매 화면은 프론트엔드다. 그런데 "이 공연에 좌석이 몇 자리 남았나", "이 주문의 총액은 얼마인가", "이 QR 코드가 진짜 발급된 티켓인가" 같은 판단은 화면이 하면 안 된다. 화면은 관객의 컴퓨터에서 도는, 관객이 마음대로 뜯어고칠 수 있는 영역이기 때문이다. 이런 판단은 우리가 통제하는 서버 — 백엔드 — 에서 해야 한다. 이 장은 바로 그 주방을 짓는 장이다.

API란 무엇이며, 왜 '명세'가 필요한가

백엔드와 프론트엔드는 서로 다른 곳에서 돌아간다(관객 컴퓨터 vs 우리 서버). 둘은 어떻게 대화할까? API(Application Programming Interface) 를 통해서다. API는 '프로그램끼리 주고받는 약속된 창구'를 말한다. 사람이 식당에서 "9번 테이블, 파스타 둘"이라고 정해진 양식으로 주문하듯, 화면은 서버에게 "EV009 공연, TT020 등급 티켓 2장 주문"이라고 정해진 양식으로 요청을 보낸다. 그 양식을 문서로 못 박아 둔 것이 API 명세서(spec) 다.

명세에는 이런 것이 적혀 있다 — 어떤 주소(경로)로, 어떤 방식(메서드)으로 요청하면, 어떤 데이터를 실어 보내야 하고, 성공하면 어떤 모양의 응답이 오고, 실패하면 어떤 코드가 오는지. 말하자면 주방과 홀이 함께 합의한 주문서 양식이다. 홀은 이 양식대로 주문을 넣고, 주방은 이 양식대로 요리를 내보낸다. 양식만 지키면, 홀과 주방은 서로의 내부 사정을 몰라도 완벽히 협업한다.

땅은 이미 다져져 있다 — 백엔드는 명세와 DB를 잇는다

백엔드가 서버 코드를 짜려면, 그 코드가 붙을 돌아가는 DB와 테이블과 데이터가 먼저 있어야 한다. "공연 목록을 돌려준다"는 코드는 공연이 담긴 테이블이 있어야 쓸 수 있고, "주문을 저장한다"는 코드는 주문을 받아 줄 테이블이 있어야 돈다. 먼저 땅을 다지고, 그 위에 집을 짓는다. 그래서 DBA가 먼저였다 — docs/ERD.md로 테이블과 컬럼과 제약을 정했고, Supabase에 실제 테이블 5개를 만들어 CSV 데이터(공연 12·티켓 등급 26·회원 50·주문 300·입장 15행)를 부어 두었다. 그리고 아키텍트는 그 ERD를 입력으로 docs/API-Spec.md를 썼다. 명세에 적힌 값은 전부 DB가 실제로 가진 값이거나, DB 값으로 계산할 수 있는 값이다.

이 장에 들어오는 지금, 손에 쥔 것을 세어 보자.

이미 있는 것 누가 만들었나 백엔드에게 무엇인가
docs/API-Spec.md 아키텍트 무엇을 주고받을지 정한 API 명세서
docs/ERD.md, api/의 DB 스키마·마이그레이션 파일 DBA 실제로 가진 값의 설계도
Supabase의 테이블 5개와 데이터 DBA 코드가 붙을 진짜 DB
api/.env의 DATABASE_URL DBA 그 DB로 가는 접속 주소
/health만 있는 api/ 골격 뼈대를 세울 때 코드를 채울 빈 집터

백엔드의 일은 이 둘 — 명세와 DB — 을 이어 붙이는 것이다. 명세가 "공연 목록 조회는 이런 모양으로 답한다"고 적어 두었으면, DB의 공연 테이블에서 값을 읽어 그 모양으로 내보내는 코드를 쓴다. 그래서 이 장에서는 코드 안에 표본 데이터를 심어 놓고 흉내 내는 단계가 없다. 첫 엔드포인트부터 진짜 DB를 읽고, 첫 주문부터 진짜 DB에 쓴다.

기준 자료가 두 개인 역할

백엔드 개발자 역할의 기준 자료는 둘이다.

기준 자료 무엇을 말해 주나 주인
API 명세서(docs/API-Spec.md) 무엇을 주고받을지 — 경로·요청 필드·응답 필드·오류 코드 아키텍트
ERD·DB 스키마(docs/ERD.md, api/의 DB 스키마) 실제로 가진 값 — 테이블·컬럼·제약 DBA

'기준 자료(source of truth)'라는 말을 한 번 짚자. 어떤 사실을 두고 여러 문서·코드가 서로 다르게 말할 때, "이것이 맞다"고 최종 판정하는 출처를 기준 자료라 한다. 주고받는 모양의 최종 판정자는 코드가 아니라 명세이고, 저장된 값의 최종 판정자는 코드가 아니라 스키마다. 코드가 이 둘과 다르면 틀린 것은 코드다 — 이 우선순위를 몸에 익히는 것이 이 장의 핵심 태도다.

먼저 명세 쪽. 백엔드가 명세와 다르게 만들면 무슨 일이 생기나 — 명세를 보고 만든 화면이 통째로 어긋난다. 필드 이름 하나만 달라도 화면에는 빈칸이 뜬다. 화면 담당자도, 나중에 합류할 QA도, 전부 같은 명세를 보고 각자 자기 일을 한다. 모두가 같은 악보를 보기 때문에 따로 연습해도 합주가 되는 것이다.

다음은 스키마 쪽. 스키마는 DBA의 것이다 — 백엔드는 스키마를 고치지 않는다. 구현하다 보면 "컬럼 하나만 더 있으면 편하겠는데" 싶은 순간이 온다. 그때 백엔드가 테이블을 슬쩍 고치면, ERD와 실제 DB가 어긋나고, ERD를 근거로 쓴 명세까지 근거를 잃는다. 반대로 컬럼이 없다고 코드 안에 값을 지어내 끼워 넣어도 안 된다. 컬럼이 더 필요하면 코드로 때우지 말고 사람에게 보고한다. 사람이 받아들이면 DBA가 ERD와 스키마를 고치고, 아키텍트가 명세를 맞추고, 그다음에야 백엔드가 코드를 쓴다. 문서가 흘러온 순서 그대로 다시 거치는 것이다.

한 가지 미리 알아 둘 것이 있다. 명세의 필드는 대개 DB의 컬럼 하나와 짝을 이룬다. CSV의 한글 항목이 DB의 어느 컬럼에 담기는지는 docs/ERD.md에서 확인한다. 다만 잔여 수량은 DB에 저장된 값이 아니라 총수량 − 판매수량으로 서버가 계산해 내보내는 값이다. 이런 '옮기기와 계산'이 곧 명세와 DB를 잇는 일의 실체다.

그래서 백엔드의 직업윤리는 한 문장이다.

명세에 있는 대로 만들고, 명세에 없는 것은 만들지 말고 질문한다.

"명세에 없지만 있으면 좋을 것 같아서" 필드를 추가하는 것은 친절이 아니라 사고다. 명세에 구멍이 보이면 코드로 때우지 말고 명세를 고치자고 제안하는 것 — 그것이 올바른 작업 순서다. (사람 개발팀에서도 똑같다. 명세 안 고치고 코드만 고치는 팀은 반드시 명세와 현실이 어긋난 채로 굳는다.)

왜 "있으면 좋을 것 같아서"가 사고가 되는지 조금 더 풀어 보자. 백엔드가 명세에 없는 할인율 필드를 선의로 하나 추가했다고 하자. 화면 담당자는 그 필드가 있는 줄 모르니 안 쓴다. 그러면 그 필드는 아무도 안 읽는 채로 응답에 실려 다니며 용량만 잡아먹는다. 반대로 화면이 어쩌다 그 필드를 발견해 쓰기 시작하면, 이번엔 명세에 없는 동작에 의존하는 코드가 생긴다. 나중에 백엔드가 그 필드를 지우는 순간 화면이 깨진다. 어느 쪽이든 "명세에 없는데 실제로는 있는" 상태가 시한폭탄이 된다. 그래서 규율은 단호하다 — 없으면 만들지 말고, 필요하면 먼저 명세에 적자고 말한다.

[짚고 가기] 이 "없으면 질문한다"는 규율은 AI 시대에 특히 중요하다. AI는 유능하고 부지런해서, 시키지 않아도 "이런 것도 있으면 편하겠네" 하며 필드나 엔드포인트를 덤으로 만들어 주려는 경향이 있다. 사람 신입이라면 눈치를 보며 안 할 일을, AI는 자신 있게 해 버린다. 그래서 백엔드 역할에게는 "친절한 초과 구현 금지"를 명시적으로 못 박아 둘 필요가 있다. 뒤에서 백엔드 역할의 금지 목록에 이 규율을 적는 이유가 여기 있다.

"서버는 클라이언트를 믿지 않는다"는 직업윤리

명세 준수와 짝을 이루는 백엔드의 두 번째 계율이 있다. 서버는 클라이언트를 믿지 않는다. 여기서 '클라이언트(client)'는 서버에 요청을 보내는 쪽 — 우리 경우 관객의 브라우저 화면을 말한다. 왜 안 믿는가? 그 화면은 관객의 컴퓨터에서 돌기 때문이다. 마음만 먹으면 관객은 브라우저 개발자 도구로 화면 코드를 뜯어고쳐, 서버에 아무 요청이나 보낼 수 있다.

구체적으로 상상해 보자. 화면에서는 "수량은 최대 4장"이라고 막아 두었다. 하지만 악의적 사용자는 그 제한을 무시하고 서버에 직접 "수량 400장" 요청을 쏠 수 있다. 화면이 "총액 99,000원"이라고 계산해 보여줬어도, 사용자는 "총액 900원"이라고 조작한 요청을 보낼 수 있다. 화면에서 이미 검사했으니 서버는 믿고 넘어가자 — 이것이 바로 사고의 지름길이다.

그래서 서버는 화면의 검사를 편의로만 취급하고, 자기 손으로 다시 검사한다. 수량이 범위 안인지, 잔여석이 충분한지, 금액이 얼마인지를 서버가 처음부터 다시 판정한다. 화면의 검사는 사용자에게 빠른 피드백을 주는 친절이고, 서버의 검사가 진짜 방어선이다. 이 한 문장이 이 장 실습의 하이라이트(금액 조작 실험)로 이어진다.

11.2 용어 정리

이 절의 용어들은 이 장 내내, 그리고 온티켓의 뒷단 전체에서 계속 쓰인다. 코드를 직접 칠 일은 없지만, AI가 만든 코드와 AI가 보내 본 요청의 결과를 읽고 판단하려면 이 말들이 손에 익어야 한다. 완벽히 외우려 하지 말고 "이런 게 있구나" 정도로 눈에 익혀 두면 실습하며 붙는다.

Hono — API 서버의 뼈대 도구

Hono는 API 서버를 만드는 작고 빠른 프레임워크다. "어떤 주소로 어떤 요청이 오면, 이 함수를 실행해서 응답해라"를 선언하는 도구라고 보면 된다. Cloudflare Workers 위에서 도는 API의 표준적 선택이고, 코드가 단순해서 AI가 특히 실수 없이 다룬다.

용어를 조금 더 풀자. '프레임워크(framework)'는 '뼈대·틀'이라는 뜻으로, 자주 하는 일을 미리 갖춰 둔 반제품이다. API 서버를 맨바닥부터 만들면 "요청을 받는 부분", "주소를 구분하는 부분", "응답을 포장하는 부분"을 전부 손으로 짜야 하는데, 프레임워크는 그 틀을 제공해서 우리는 알맹이(핵심 로직)만 채우면 되게 해 준다. 집을 지을 때 기둥과 골조가 이미 서 있는 상태에서 방을 꾸미는 것과 같다.

'Hono(ホノ)'는 일본어로 '불꽃'이라는 뜻이다. 이름값처럼 아주 빠르고 가벼운 것이 특징이다. 비슷한 도구로 오래된 Express(익스프레스)가 있는데, Hono는 그보다 훨씬 가볍고, 무엇보다 Cloudflare Workers 같은 최신 실행 환경에서 잘 돈다. 우리가 온티켓 API를 Cloudflare Workers에 올릴 계획이라 Hono가 자연스러운 짝이다.

도구 성격 온티켓에서
Hono 가볍고 빠름, 최신 환경(Workers 등)에 최적 우리가 쓰는 것
Express 가장 오래되고 자료 많음, 전통적 서버에 강함 안 씀(무겁고 Workers와 궁합이 덜함)
Fastify 성능 지향, 기능 풍부 안 씀(이번 규모엔 과함)

지금 단계에서 이 비교를 외울 필요는 없다. "API 서버 뼈대는 여러 선택지가 있고, 우리는 가볍고 AI가 실수 없이 다루는 Hono를 골랐다" 정도면 충분하다.

라우트와 핸들러

라우트(route) 는 "메서드 + 경로"의 조합 하나다. 예를 들어 명세가 공연 목록 조회를 GET /events로, 주문 생성을 POST /orders로 정했다면 각각이 라우트다(실제 경로는 아키텍트가 화면기획서를 보고 명세에 정한 것이라 내 명세와 다를 수 있다). 핸들러(handler) 는 그 라우트에 요청이 왔을 때 실행되는 함수다. Hono 코드에서 이 둘은 이렇게 생겼다.

// 라우트 파일 (발췌 예시 — 경로는 설명용)
app.get('/events/:id', (c) => {          // ← 라우트: GET /events/:id
  const id = c.req.param('id')            // ← 경로에서 :id 부분을 꺼낸다
  const event = findEvent(id)             //    (예: EV009)
  if (!event) return c.json({ error: 'NOT_FOUND' }, 404)
  return c.json(event)                    // ← JSON으로 응답
})                                        //    이 함수 전체가 핸들러

코드를 전부 이해할 필요는 없다 — 어차피 작성은 AI가 한다. 다만 구조를 읽을 수 있으면 리뷰가 가능해진다: "GET /events/:id 에 (요청이 오면) → id를 꺼내 → 찾아보고 → 없으면 404, 있으면 JSON." 이 정도로 읽히면 충분하다.

용어의 뜻을 비유로 마저 잡자. '라우트(route)'는 원래 '길·경로'라는 뜻이다. 우체국이 주소를 보고 편지를 알맞은 동네로 보내듯, 서버도 들어온 요청의 '메서드+경로'를 보고 알맞은 처리 담당에게 보낸다. 이 길 배정을 '라우팅(routing)'이라 하고, 배정된 목적지 하나하나가 라우트다. '핸들러(handler)'는 '처리하는 사람'이라는 뜻으로, 그 목적지에서 실제로 일을 하는 담당 직원이다. 정리하면 — 라우트는 주소, 핸들러는 그 주소의 담당자다.

'메서드(method)'라는 말도 여기서 짚자. 같은 주소라도 "무엇을 하러 왔는가"에 따라 요청의 종류가 다르다. 이 종류를 HTTP 메서드라 부른다. 우리 장에서 쓰는 것은 둘뿐이다.

메서드 뜻 온티켓 예
GET 조회한다(가져오기만, 아무것도 바꾸지 않음) 공연 목록 조회 (예: GET /events)
POST 생성한다·처리한다(서버 상태를 바꿈) 주문 생성 (예: POST /orders)

GET은 "보여만 주세요"라 몇 번을 눌러도 안전하고, POST는 "이걸 만들어 주세요"라 누를 때마다 새 주문이 생긴다. 그래서 뒤에서 보듯 GET은 브라우저 주소창으로도 시험할 수 있지만, POST는 Swagger UI 같은 도구로 본문을 실어 보내야 한다.

요청에 데이터가 실려 오는 세 가지 길

요청은 그냥 주소만 오는 게 아니라, 대개 데이터를 함께 싣고 온다. 데이터가 실려 오는 길은 세 가지다. 이 셋을 구분하는 것이 API를 읽는 기본기다.

길 생김새 (예시 경로) 쓰임
경로 파라미터 /events/EV009 의 EV009 "어느 것"을 지목할 때
쿼리 /events?category=콘서트 필터·검색 조건
본문(body) POST 요청에 실리는 JSON 만들 데이터 (주문 내용 등)

표의 경로는 설명을 위한 예시다. 세 길을 우체국 비유로 이어 보자. 경로 파라미터는 주소 자체에 박혀 있는 번지수다 — 예시의 /events/EV009는 "EV009라는 그 공연"을 콕 집는다. 하나를 지목할 때 쓴다. 쿼리(query) 는 주소 뒤에 ?로 붙는 조건표다 — ?category=콘서트는 "콘서트만 골라 줘"라는 검색·필터 조건이다. '쿼리'는 '질의·물음'이라는 뜻이라, "이런 조건으로 물어본다"고 기억하면 된다. 본문(body) 은 봉투 안에 넣어 보내는 내용물이다 — 주소만으로 표현하기엔 큰 데이터(주문 내역 같은)를 JSON 형태로 실어 보낸다.

앞 장에서 배운 'JSON(제이슨)'도 다시 짚어 보자. JSON은 프로그램끼리 데이터를 주고받을 때 쓰는 표준 표기법으로, {"이름": "값", "이름2": "값2"}처럼 '이름:값' 쌍을 중괄호로 묶은 모양이다. 사람도 읽을 수 있을 만큼 단순해서, 오늘날 대부분의 API가 JSON으로 요청·응답을 주고받는다. 이 장의 응답과 요청에서 계속 보게 될 모양이다.

상태 코드 — 응답에 붙는 세 자리 숫자

API 응답에는 본문(JSON)만 오는 게 아니라, "결과가 어땠는가"를 알리는 세 자리 숫자 — HTTP 상태 코드(status code) — 가 함께 온다. 이 장에서 우리가 일부러 만들어 낼 코드들이라 미리 정리해 둔다.

코드 뜻 온티켓에서 언제
200 OK 성공(조회) 공연 목록 조회가 목록을 잘 돌려줄 때
201 Created 성공(생성됨) 주문 생성으로 주문이 새로 만들어질 때
400 Bad Request 요청이 잘못됨(사용자 탓) 수량이 1~4 범위 밖일 때
404 Not Found 그런 것 없음 없는 이벤트 ID(EV999)를 찾을 때
409 Conflict 충돌(상태가 안 맞음) 잔여석보다 많이 주문할 때

숫자의 앞자리로 큰 뜻을 가른다 — 2xx는 성공, 4xx는 요청자(클라이언트)의 잘못, 5xx는 서버의 잘못이다. 특히 이 장의 주인공은 409다. '409 Conflict'는 "요청 자체는 형식이 맞지만, 지금 서버의 상태와 부딪혀서(충돌해서) 들어줄 수 없다"는 뜻이다. 남은 좌석이 2석인데 4석을 달라는 주문이 딱 이 경우다 — 요청 형식은 멀쩡한데 재고와 충돌한다. 그래서 초과 주문의 표준 응답이 409다.

'오류를 200으로 포장하지 말라'는 규율(뒤에서 볼 백엔드 역할의 금지 목록)이 왜 중요한지 여기서 이어진다. 실패했는데도 200(성공)을 돌려주고 본문에만 "실패"라고 적으면, 화면과 다른 시스템은 겉의 200만 보고 "성공했구나" 오해한다. 실패는 반드시 4xx/5xx 상태 코드로 정확하게 전달해야 한다.

검증 (validation)

들어온 요청이 약속(명세)대로인지 검사하는 것. 수량이 1~4 사이인가, 이메일 형식이 맞는가, 잔여석이 충분한가. 서버는 클라이언트를 믿지 않는다가 원칙이다 — 화면에서 이미 검사했더라도 서버는 다시 검사한다. 화면 검사는 사용자 편의고, 서버 검사가 진짜 방어선이다.

'검증(validation)'은 '유효한지(valid) 확인한다'는 뜻이다. 검증에는 성격이 다른 두 가지가 있다는 걸 알아 두면 좋다. 하나는 형식 검증 — 수량이 숫자인가, 이메일에 @가 있는가 처럼 요청의 생김새를 보는 것. 다른 하나는 규칙 검증 — 잔여석이 충분한가, 이 등급이 이 공연에 실제로 있는가처럼 우리 데이터·비즈니스 규칙과 대조하는 것. 형식 검증은 문지기가 신분증 양식을 보는 것이고, 규칙 검증은 명단과 실제로 대조하는 것이다. 둘 다 통과해야 요청을 받아들인다.

개념 절에서 말한 "서버는 클라이언트를 믿지 않는다"가 여기서 실체를 얻는다. 화면이 아무리 꼼꼼히 검사해도, 그 검사는 관객 컴퓨터에서 도는 코드라 우회당할 수 있다. 그래서 서버는 같은 검사를 한 번 더, 자기 손으로 한다. 중복처럼 보여도 이 중복이 방어선이다.

Swagger UI — 브라우저에서 API를 눌러 보는 화면

브라우저 주소창은 GET만 보낼 수 있다. 주문 생성 같은 POST는 본문을 실어야 해서 주소창으로는 시험할 수 없다. 화면 없이 POST까지 보내 보는 도구는 두 가지가 흔하다. 터미널 명령인 curl과, 웹 화면인 Swagger UI다. 이 장에서는 Swagger UI를 쓴다.

Swagger UI는 API의 엔드포인트 목록을 웹 페이지 하나로 보여 준다. 엔드포인트를 펼치면 무엇을 보내야 하는지가 나오고, Try it out을 눌러 값을 채운 뒤 Execute를 누르면 요청이 실제로 나간다. 상태 코드와 응답은 바로 아래에 찍힌다. 요청 본문도 화면에서 직접 고칠 수 있어서, 금액을 몰래 끼워 넣는 시험도 손으로 해 볼 수 있다.

Swagger UI가 엔드포인트 목록을 아는 것은 OpenAPI 문서 덕분이다. OpenAPI는 API 명세를 프로그램이 읽을 수 있게 적는 표준 형식이다. 우리 명세는 사람이 읽는 문서라, Claude Code가 그 내용을 OpenAPI로 옮기고 Swagger UI를 붙인다. 사람은 "Swagger UI 띄워줘" 한마디면 된다.

Swagger UI의 주소는 대개 localhost:8787 같은 모양이다. localhost는 '내 컴퓨터 자신'을 가리키는 주소이고, :8787은 그 안에서 우리 api 서버가 듣고 있는 문(포트) 번호다. 아직 인터넷에 올린 것이 아니라 내 컴퓨터 안에서만 도는 상태다.

[짚고 가기] curl은 배포한 서버를 확인할 때 다시 나온다. 터미널에서 한 줄로 요청을 보내는 도구라, 서버가 살아 있는지 빠르게 볼 때 쓴다. 명령을 외울 필요는 없다 — AI에게 보내게 하고 결과를 읽으면 된다.

11.3 백엔드 역할 정의 — 네 항목과 스킬

앞선 장들에서 역할을 '판단 기준·금지 목록·프로세스·도구 권한'의 네 항목으로 설계했다. 백엔드 역할도 같은 틀로 정의한다. 여기에 이 역할이 하는 일과 기준 자료를 앞에 적는다.

이 항목들을 사람이 다 적어 주지는 않는다. 사람이 말하는 것은 이 역할이 하는 일, 기준으로 삼을 문서, 그리고 온티켓에서 사고가 나는 지점 몇 줄이다. 나머지는 AI가 문서를 읽고 채운다. 대신 사람은 만들어진 스킬 파일을 읽고 빠진 것을 찾아야 한다. 아래 표가 그 기준이다.

항목 잘 쓴 정의에 들어 있는 것
하는 일 API 명세서의 엔드포인트를 api/ 에 구현한다
기준 자료 주고받는 모양은 API 명세서, 실제로 가진 값은 ERD와 DBA가 만든 스키마. 코드 배치는 회사 가이드 문서. 데이터는 언제나 DB에서 읽고 DB에 쓴다
판단 기준 잔여·금액 같은 판정은 서버가 하고, 요청에 실려 온 값은 믿지 않는다. DB를 여러 번 고치는 일은 함께 성공하거나 함께 실패하게 묶는다. 명세에 없는 세부는 명세의 공통 규칙대로 정하고 보고에 적는다
프로세스 명세·ERD 확인 → 구현 → 명세와 대조 → 보고. 명세나 ERD를 바꿔야 하는 문제는 고치지 않고 보고한다
금지 목록 명세에 없는 엔드포인트·필드 추가 / API 명세서 수정 / 코드 안에 임시 데이터 심기
도구 권한 api/ 안에서 작업한다. 화면(web/)과 DB 스키마·마이그레이션은 고치지 않는다

각 항목에 왜 그 내용이 들어가야 하는지 풀어 둔다. 스킬 파일을 검토할 때 이 설명이 기준이 된다. 그리고 이 항목들이 채워져 있는 만큼, 뒤에서 /backend에게 일을 시키는 말이 짧아진다.

  • 기준 자료는 이 역할이 무엇을 최고 권위로 삼는지다. 코드가 명세나 스키마와 다투면 지는 쪽은 코드다. 명세의 필드와 DB 컬럼의 대응도 새로 정하지 않는다 — docs/ERD.md가 이미 정해 두었다. "데이터는 언제나 DB에서 읽고 DB에 쓴다"는 데이터의 출처를 못 박는 줄이다. 연결 정보는 DBA와 작업할 때 만들어 둔 api/.env에 있고, 테이블의 모양은 DBA가 만든 스키마에 있다. 백엔드는 이 둘을 그대로 가져다 쓸 뿐 새로 만들지 않는다.
  • 판단 기준의 "판정은 서버가 하고, 요청에 실려 온 값은 믿지 않는다"는 개념 절의 '클라이언트를 믿지 않는다'를 규칙으로 옮긴 것이고, 이 장 전체의 안전판이다. 악의적 사용자가 브라우저에서 금액을 99000→900으로 조작해 보내는 일은 실제로 일어난다. 서버가 스스로 계산하는 것만이 방어다. 주문 생성에는 사고가 날 지점이 최소 셋이다 — 금액(조작), 재고(초과), 수량(범위). 이 셋을 구현을 시킬 때마다 기억해 내서 적는 대신, 이 한 줄을 역할에 적어 두면 어느 엔드포인트를 시키든 함께 적용된다.
  • 같은 항목의 "함께 성공하거나 함께 실패하게 묶는다"도 짚자. 주문 행은 저장됐는데 판매수량은 안 늘었다면, 장부상 좌석이 남아 있는 것처럼 보여 그 좌석이 또 팔린다. 여러 번의 DB 쓰기를 하나로 묶어 '전부 되거나 전부 안 되게' 만드는 장치를 트랜잭션(transaction) 이라 한다. 구현은 AI가 하지만, 이 요구를 역할에 적는 것은 사람의 몫이다.
  • 판단 기준의 마지막 줄 "명세에 없는 세부는 정하고 보고에 적는다"는 일이 멈추지 않게 하는 줄이다. 구현하다 보면 주문번호의 모양, 목록의 정렬 순서처럼 명세에 적히지 않은 세부가 나온다. 이런 것을 하나하나 사람에게 묻게 하면 일이 멈추고, 사람이 정할 근거도 딱히 없다. 그래서 AI가 정하고 무엇을 왜 그렇게 정했는지만 보고받는다. 금지 목록의 "명세에 없는 엔드포인트·필드 추가"와 부딪히지 않는다 — 주고받는 모양은 명세가 정하고, 그 안쪽의 구현 방식을 AI가 정하는 것이다.
  • 프로세스에서 눈여겨볼 곳은 '명세와 대조' 단계와 마지막 문장이다. 구현하고 곧바로 "다 됐습니다"로 가지 않고, 만든 것을 명세와 한 항목씩 맞춰 본 뒤 보고한다. 그리고 명세나 ERD를 바꿔야 하는 문제는 고치지 않고 보고한다. 명세를 고칠지 코드를 고칠지는 결정이고, 결정은 사람 몫이다. 이 줄이 없으면 AI는 어긋난 곳을 발견하는 즉시 자기가 옳다고 본 쪽으로 조용히 고쳐 버린다.
  • 금지 목록은 이 역할이 저지르기 쉬운 사고를 미리 막는 울타리다. "명세에 없는 엔드포인트·필드 추가"는 앞에서 본 '친절한 초과 구현'을 막는다. "코드 안에 임시 데이터 심기"는 눈에 잘 안 띄는 사고를 막는다 — 이 줄이 없으면 AI는 DB 연결이 번거로울 때 코드 안에 공연 몇 개를 적어 넣고 "됩니다"라고 보고할 수 있다. 응답은 똑같이 생겼으니 눈으로는 구분되지 않는다. "API 명세서 수정 금지"는 명세를 한쪽이 말없이 바꾸는 일을 막는다. 명세는 화면과 서버가 함께 기대는 문서라, 고칠 일이 생기면 사람에게 보고하고 /architect를 거친다.
  • 도구 권한은 이 역할이 작업할 수 있는 범위다. 남의 영역 — DBA의 스키마, 프론트엔드의 web/ — 을 건드리지 않게 하는 선이다. 스키마 파일이 같은 api/ 폴더 안에 있어 손이 닿는다는 점이 함정이라, 따로 적어 둔다. 테이블을 지우는 명령은 DBA와 작업할 때 걸어 둔 Hook이 한 번 더 막는다.

이것을 스킬로 만들어 두면 /backend 한마디로 이 규율이 적용된다.

'스킬(skill)'이라는 말을 다시 짚자. 스킬은 이 역할 정의를 파일 하나에 담아 둔 것이다. 매번 "명세가 기준이고, 판정은 서버가 하고…"를 다시 설명하는 대신, /backend라고 부르기만 하면 이 규율 전체가 한꺼번에 적용된다. 회사로 치면 '백엔드 개발자 직무기술서'를 한 장으로 정리해 두고, 새 일을 줄 때마다 그 직무기술서를 첨부하는 것과 같다.

명세 기반으로 일하는 방식은 실무 어디에나 있다 — 이 역할 정의는 온티켓 전용이 아니다.

  • 사내 시스템 연동 개발: 연동 명세가 법. 명세에 없는 데이터를 임의로 보내면 장애
  • 공공데이터·오픈API 활용: 상대방 명세를 그대로 따르는 클라이언트를 만든다
  • 챗봇·자동화 봇의 백엔드: 메신저 플랫폼의 명세대로 응답 형식을 맞춘다
  • 엑셀 자동화조차: "이 열은 이 형식"이라는 서식 정의가 명세 역할을 한다

이 사례들을 조금 더 구체화하면 '명세가 법'이라는 감각이 온티켓 밖으로도 확장된다.

  • 은행·결제 연동: 결제사(예: 토스페이먼츠)가 준 연동 명세는 한 글자도 우리 마음대로 못 바꾼다. 명세가 요구하는 필드를 정확히, 요구하는 형식으로 보내야 승인이 난다. 여기서 "있으면 좋을 것 같아서" 필드를 더 보내면 오히려 거절당한다. 상대의 명세가 곧 법이다.
  • 배송사 API 연동: 택배사 시스템에 운송장을 등록할 때, 주소·수량·상품명의 형식이 명세에 못 박혀 있다. 이 형식을 어기면 물건이 엉뚱한 곳으로 가거나 등록 자체가 실패한다.
  • 공공데이터 포털: 정부가 공개한 날씨·교통 API는 우리가 손댈 수 없는 남의 서버다. 우리는 그 명세를 그대로 따르는 '읽는 쪽(클라이언트)'을 만들 뿐이다.
  • 사내 부서 간 협업: 마케팅팀 시스템과 회원 시스템이 데이터를 주고받을 때도, 두 팀이 합의한 필드 정의가 명세다. 한쪽이 말없이 필드 이름을 바꾸면 다른 쪽이 깨진다 — 온티켓 안에서 백엔드와 화면이 어긋나는 것과 똑같은 사고가, 회사 규모에서 일어나는 것이다.

즉 '명세대로, 없으면 질문'은 온티켓 백엔드의 특수 규율이 아니라, 시스템과 시스템이 협업하는 모든 자리의 공통 직업윤리다. 이 장에서 그 감각을 몸에 익히면, 나중에 어떤 연동을 맡아도 첫 질문이 "명세는 어디 있나요?"가 된다.

[짚고 가기] 이 절은 자칫 딱딱한 규칙 나열로 읽히기 쉽다. 실무 사례(특히 결제·배송 연동에서 명세를 어겨 사고 난 이야기)를 함께 떠올리면 규율의 무게가 살아난다. "명세에 없는 필드를 선의로 더 보냈다가 상대 시스템이 거절해 결제가 다 실패한" 류의 사고는 업계에 흔하다. 규칙을 외우기보다 "왜 그래야 하는지"를 사례와 함께 붙잡아 두면 오래 남는다.

11.4 프롬프트 작성법 — 명세를 기준으로 구현을 맡긴다

이 절의 프롬프트들이 이 장의 실전 핵심이다. 그런데 읽어 보면 놀랄 만큼 짧다. 공통된 발상은 하나다. 기준은 명세와 역할 정의에 적어 두고, 지시에서는 그 자료를 지정한다. 백엔드에게 "잘 만들어 줘"라고 하지 않는 것은 그대로다. 다만 "명세대로, 없는 필드는 넣지 말고, DB에서 읽고, 스키마는 건드리지 말고, 끝나면 명세와 대조해서…"를 매번 손으로 적지도 않는다. 그 말은 전부 /backend 역할 정의에 이미 들어 있기 때문이다.

표의 위 일곱 줄은 명세나 스킬에 이미 적혀 있다. 아래 네 줄은 사람이 이번 작업에서 직접 정해야 한다. 프롬프트에 조건을 길게 적고 있다면, 그 조건이 있어야 할 역할 정의나 명세가 비어 있다는 신호다. 그럴 때는 프롬프트를 늘리지 말고 문서를 채운다.

구현 지시 — 명세의 엔드포인트를 한 번에 맡긴다

프롬프트
/backend 명세의 엔드포인트를 전부 구현해줘. 결제 승인은 뒤에서 따로 붙일 거니까 이번엔 빼줘.주문이 저장되면 그 등급의 판매수량도 주문 수량만큼 늘어야 해.확인은 내가 따로 시킨다. DB에 시험 데이터를 넣거나 값을 바꾸지 마.

세 줄이다. 이 지시가 왜 이것으로 충분한지 뜯어 보자.

첫 줄은 기준 문서를 가리키고 범위를 말한다. 엔드포인트의 이름도 경로도 적지 않는다. 어떤 엔드포인트가 있고 각각 어떤 메서드와 경로를 쓰는지는 아키텍트가 정해 명세에 적어 두었다. /backend로 역할을 부르면 "명세에 없는 엔드포인트·필드는 만들지 않는다", "데이터는 DB에서 읽고 쓴다", "스키마는 고치지 않는다", "끝나면 명세와 대조해 보고한다"가 전부 딸려 온다. 어디에 구현할지(api/)조차 역할에 있어서 적지 않는다. 첫 지시를 배울 때 익힌 '목표 + 완료 기준 + 제약'의 기본형에서, 완료 기준과 제약이 명세와 역할 정의로 옮겨 가고 목표만 남은 모습이다.

사고 나는 지점도 명세에 못 박혀 있다. 주문 생성에는 사고가 날 지점이 최소 셋이다 — 금액(조작), 재고(초과), 수량(범위). 수량은 1~4이고 범위 밖이면 400, 잔여가 부족하면 409, 성공하면 201과 주문번호, 상태 결제대기 — 이것은 전부 docs/API-Spec.md의 주문 생성 항목에 적혀 있다. 아키텍트와 명세를 검토할 때 409가 적혀 있는지 굳이 확인한 이유가 여기서 드러난다. 금액을 서버가 계산하고 요청에 실려 온 금액을 믿지 않는 것은 /backend의 판단 기준이 들고 있다. 명세의 상태 코드를 사람이 기억으로 다시 받아 적는 것은 위험하기도 하다 — 기억이 명세와 한 글자라도 다르면 AI는 서로 다른 두 지시를 받은 셈이 된다.

그럼 둘째 줄은 왜 남았는가. 명세는 요청과 응답만 적는다. "주문이 들어가면 그 등급의 판매수량이 는다"는 것은 응답에 드러나지 않는 부수 효과라 명세에는 없다. ERD 결정 기록에 "주문할 때 자리를 잡는다"가 있어도, 주문 저장과 판매수량 증가를 한 묶음으로 하라는 말은 구현을 시킬 때 사람이 짚는다. 이 줄이 있으면 역할의 판단 기준 "함께 성공하거나 함께 실패하게 묶는다"가 주문 저장과 판매수량 증가에 그대로 적용된다.

셋째 줄은 확인의 주인을 정한다. 이 줄이 없으면 AI는 구현을 마친 뒤 확인하겠다며 시험 주문을 DB에 넣고 판매수량을 바꾼다. 실습의 시험 데이터가 미리 섞이면, 사람이 나중에 주문을 보내 보고 DB를 열어 대조할 때 무엇이 방금 생긴 것인지 구분할 수 없다. 확인은 사람이 다음 단계에서 순서대로 시킨다.

구현하다 보면 명세에도 ERD에도 적히지 않은 세부가 나온다 — 주문번호를 어떤 모양으로 만들지, 두 쓰기를 어떤 방식으로 묶을지 같은 것. 이것도 프롬프트에 적지 않는다. /backend가 정하고 정한 것과 이유를 보고에 적는다는 것이 역할의 판단 기준에 있다. 사람은 그 보고를 읽고, 명세를 바꿔야 할 결정이 섞여 있으면 /architect에게 돌린다.

여기서 중요한 규칙 하나. 명세에 없는 규칙이 떠오르면 프롬프트에 적지 말고, /architect로 명세부터 고친다. 예를 들어 "같은 이메일로는 한 공연에 한 번만 주문할 수 있게 하자"는 생각이 들었다고 하자. 이것을 /backend 지시에 한 줄 끼워 넣으면 그 규칙은 코드에만 살고 명세에는 없는 규칙이 된다. 화면을 만드는 쪽은 그런 거절이 있는 줄 모른 채 명세만 보고 만든다 — 앞에서 본 '명세에 없는데 실제로는 있는' 시한폭탄을 사람이 직접 심는 것이다. 규칙은 명세에 먼저 적고, 백엔드에게는 여전히 "명세의 엔드포인트를 구현해줘"라고만 말한다.

그렇다고 역할과 명세를 믿고 눈을 감는 것은 아니다. 구현했다는 말을 믿지 않는다. 구현 보고에 명세와 대조한 결과가 함께 와도, 그것은 AI의 주장이다. 사람은 Swagger UI에서 직접 요청을 보내 보고, Supabase를 열어 DB에 무엇이 남았는지 본다. 그 확인이 실습의 나머지 전부다.

약한 지시 → 강한 지시 (백엔드판)

같은 목표라도 지시를 어떻게 적느냐에 따라 결과가 갈린다. 첫 지시를 배울 때 본 약한 지시 → 강한 지시 변환표를 백엔드 상황으로 옮겨 본다. 여기서 약한 지시는 역할도 문서도 없이 던지는 한 줄이고, 강한 지시는 역할과 문서 위에서 하는 짧은 말이다. 길이는 거의 같다. 강한 쪽이 강한 이유는 문장이 길어서가 아니라, 그 문장이 기댈 기준이 있어서다.

핵심 감각은 그때와 같다 — 막연한 형용사('잘', '보안 신경 써서')를 눈으로 확인 가능한 규칙과 완료 기준으로 바꾼다. 백엔드에서는 그 규칙이 대개 "어떤 상황에 어떤 상태 코드를 돌려준다"의 형태를 띤다. 달라진 것은 그 규칙을 적어 두는 자리다. 프롬프트가 아니라 명세와 역할 정의에 적는다. 셋째·넷째 줄처럼, 막연한 걱정이 들 때 할 일이 "지시를 더 보태는 것"이 아니라 "문서를 확인하는 것"과 "직접 시험하는 것"인 경우도 많다.

수정 지시의 예 — 불일치가 나왔을 때

구현 보고나 시험에서 명세와 어긋난 곳이 나오면, 고치는 지시에는 방향을 명확히 실어 준다. 이것은 사람이 지금 내리는 결정이라 프롬프트에 적어야 하는 말이다. 결정은 사람이 하고, 실행만 AI에게 넘기는 리듬이다. 방향에 따라 받는 역할이 달라진다는 점에 주의하자. 아래 표의 말은 예시다. 따옴표 안의 불일치는 지어낸 것이니, 실제로는 구현 보고나 시험에서 나온 항목으로 바꿔 말한다.

결정 받는 역할 말의 예
명세가 맞다 — 코드를 고친다 /backend /backend 구현 보고에 나온 '응답의 잔여 수량 필드가 명세엔 있는데 코드엔 빠짐'은 코드를 고쳐서 맞춰줘. 명세는 그대로 두고.
코드가 맞다 — 명세를 고친다 /architect /architect 구현 보고에 나온 '응답의 매진 여부 필드가 코드엔 있는데 명세엔 없음'은 코드가 맞다고 판단했어. 명세에 그 필드를 추가하고, 왜 필요한지도 한 줄 남겨줘.

명세 쪽을 고칠 때 받는 역할이 아키텍트인 것은, 백엔드는 docs/API-Spec.md를 직접 고치는 것이 금지이기 때문이다. 첫 줄의 "명세는 그대로 두고", 둘째 줄의 "코드가 맞다고 판단했어"처럼 어느 쪽이 기준인지를 말 안에 드러내는 것이 요령이다.

두 경우의 공통점은 "무엇을 기준으로 삼을지(명세 vs 코드)를 사람이 먼저 정하고, AI에게는 그 방향으로 맞추는 실행만 시킨다"는 것이다. 이것이 백엔드 역할 프로세스의 '보고 → (사람의 결정) → 수정'이 실제로 도는 모습이다. 불일치가 명세와 코드 사이가 아니라 명세와 DB 사이에서 나왔다면(명세에는 있는데 DB에는 없는 값) 백엔드 선에서 풀 일이 아니다. 사람이 DBA와 아키텍트를 다시 불러 ERD와 명세부터 맞춘다.

[짚고 가기] 이 절은 프롬프트를 '읽는' 것으로 끝내지 말고, 하나라도 직접 넣어 보면 좋다. 특히 비교해 볼 만한 것은 이 둘이다 — /backend 스킬도 명세도 없는 빈 대화에서 "주문 API 만들어줘"라고 던졌을 때와, 스킬과 명세 위에서 "/backend 명세의 주문 생성을 구현해줘"라고 했을 때. 두 지시의 길이는 거의 같은데 결과는 다르다. 빈 대화에서도 AI가 곧잘 만들긴 하지만, 금액 조작을 막는지·409를 정확히 쓰는지는 그때그때 운에 달린다. 역할과 명세 위에서는 그것이 훨씬 안정적이다. 차이를 만든 것은 프롬프트의 문장이 아니라 그 문장이 기대고 있는 문서다. '지시에 규칙을 싣는다'가 아니라 '규칙은 문서에 싣고, 지시는 그 문서를 가리킨다'는 감각을 여기서 가져가자.

11.5 실습 — 온티켓 API를 세운다

이제 실제로 온티켓의 뒷단을 세운다. 목표는 명확하다 — 화면 없이도, Swagger UI에서 보내는 요청만으로 "이벤트가 조회되고, 주문이 만들어지고, 초과 주문은 거절되고, 금액 조작은 무시되는" API를 눈으로 확인하는 것이다. 그리고 매번 Supabase 대시보드를 함께 열어, 그 데이터가 정말 DB에서 나오고 DB로 들어가는지를 대조한다.

[잠깐] 시작 전에 확인한다. docs/ERD.md, docs/API-Spec.md, api/.env의 DATABASE_URL, 그리고 Supabase 대시보드의 테이블 5개(데이터 포함)가 있어야 한다. 하나라도 없으면 이 장의 지시는 기댈 땅이 없다 — DBA와 아키텍트의 작업을 먼저 끝낸다.

따라하기 1 — 백엔드 스킬 생성

프롬프트
'백엔드 개발자' 스킬을 만들어줘. 이름은 backend로 해. 서버(API) 구현을 담당한다.docs/API-Spec.md·docs/ERD.md와 docs/가이드/의 문서를 기준으로 api/에 구현한다. 라이브러리는 최신 공식 문서를 확인해서 쓰고, 필요한 의존성은 알아서 추가한다.데이터는 언제나 DB에서 읽고 쓴다. 잔여·금액 같은 판정은 서버가 하고, 요청에 실려 온 값은 믿지 않는다. 주문처럼 DB를 여러 번 고치는 일은 함께 성공하거나 함께 실패하게 묶는다.화면, DB 스키마·마이그레이션, API 명세서는 수정하지 않는다. 명세에 없는 엔드포인트·필드는 만들지 않는다. 명세에 없는 세부는 명세의 공통 규칙대로 정하고 보고에 적는다. 명세나 ERD를 바꿔야 하는 문제는 고치지 말고 보고한다.

위 프롬프트를 그대로 복사해 입력하면 된다. /를 눌러 backend가 목록에 있는지 확인한다.

사람이 적은 것은 하는 일, 기준 문서, 그리고 온티켓에서 사고가 나는 지점이다. 셋째 줄의 두 문장 — "요청에 실려 온 값은 믿지 않는다"와 "함께 성공하거나 함께 실패하게 묶는다" — 이 그것이다. 나머지 항목은 AI가 문서를 읽고 채운다. 뒤따르는 구현 지시들이 한두 줄로 끝나는 것은 조건을 여기에 적어 두었기 때문이다.

만들어진 스킬 파일을 열어, 위 역할 정의 표의 항목이 빠짐없이 들어갔는지 확인한다. 특히 세 가지를 본다 — "요청에 실려 온 값은 믿지 않는다", "데이터는 DB에서 읽고 쓴다(코드 안에 임시 데이터를 두지 않는다)", "명세에 없는 엔드포인트·필드는 만들지 않는다". 뒤의 따라하기에서 프롬프트에 적지 않고 이 파일에 기대는 줄들이다. 빠졌다면 다시 넣게 한다.

구현이 끝나면 보고를 읽는다. 두 가지가 들어 있어야 한다.

  • AI가 정한 것 — 주문번호의 모양, 정렬 순서, 빈 목록일 때의 모양 같은 세부. 명세를 바꿔야 하는 결정이 섞여 있으면 /architect에게 돌린다. 나머지는 그대로 둔다

응답만 보지 말고 Supabase 대시보드를 열어 DB에 남은 것을 확인한다.

  • 주문 테이블에 방금 주문의 새 행이 결제대기로 있고, 금액이 서버가 계산한 값이다
  • 티켓 등급 테이블의 판매수량이 주문 수량만큼 늘었다
  • 입장 기록 테이블에 행이 하나 늘었다
  • 판매 현황 조회의 잔여가 (총수량 − 판매수량)과 같다

기대와 다른 결과가 나오면, 명세를 고칠지 코드를 고칠지 사람이 정해서 지시한다. 코드를 고치면 /backend에게, 명세를 고치면 /architect에게 시킨다.

완료 기준 체크리스트

  • /backend 스킬이 등록되어 있다
  • 구현 보고에서 명세의 엔드포인트가 전부 구현됐음을 확인했고, AI가 정한 세부를 읽었다
  • Swagger UI에서 눌러 본 결과가 위 기대 응답과 맞는다
  • 주문에 조작한 금액을 넣어도 서버가 계산한 금액으로 처리된다
  • 주문 후 Supabase 주문 테이블에 새 행이 생기고 판매수량이 늘었다

11.6 정리

  • 백엔드의 직업윤리는 "명세 그대로, 없으면 질문"이다. 명세의 구멍은 코드로 때우지 않고 명세를 고치자고 제안한다 — 사람 팀에서도 AI 팀에서도 같다.
  • 백엔드는 명세와 DB를 잇는 일이다. 서버 코드는 붙을 DB가 있어야 쓸 수 있어서 DBA가 먼저였고, 그 DB를 입력으로 명세가 쓰였다. 그래서 첫 엔드포인트부터 진짜 DB에 연결한다.
  • 기준 자료는 둘이다 — API 명세서(무엇을 주고받을지)와 ERD·DB 스키마(실제로 가진 값). 스키마는 DBA의 것이라 백엔드는 고치지 않는다. 컬럼이 모자라면 코드로 때우지 않고 사람에게 보고해 DBA·아키텍트를 거친다.
  • 구현 지시는 짧다. 사고 나는 지점은 명세에, 울타리는 /backend 역할 정의에 못 박혀 있어서 지시는 그것을 가리키기만 한다. 프롬프트에 적는 것은 사람만 아는 것 — 이번 일의 범위, 명세에 없는 부수 효과, 불일치를 어느 쪽으로 고칠지 — 뿐이다. 명세에 없는 규칙이 떠오르면 프롬프트에 적지 말고 /architect로 명세부터 고친다.
  • DB 연결은 응답이 아니라 DB를 열어서 증명한다. 주문 후 주문 테이블에 행이 생기고 판매수량이 늘었는가.
  • 라우트는 "메서드+경로", 핸들러는 그때 실행되는 함수. 코드를 다 못 읽어도 구조가 읽히면 리뷰할 수 있다.
  • 요청에 데이터가 실려 오는 길은 셋(경로 파라미터·쿼리·본문)이고, 응답에는 상태 코드가 붙는다. 특히 초과 주문은 409(충돌)로 거절하는 것이 표준이다. 코드의 409가 첫 번째 문, DB의 CHECK 제약이 마지막 문이다(다층 방어).
  • 서버는 클라이언트를 믿지 않는다. 화면의 검사는 편의, 서버의 검사가 방어선. 금액은 요청에 실려 와도 무시하고 서버가 계산한다 — Swagger UI에서 직접 보내 확인했다.
  • GET은 브라우저 주소창으로도 시험할 수 있지만 POST는 본문을 실어야 해서 도구가 필요하다. Swagger UI를 띄우면 명세의 엔드포인트를 화면에서 직접 눌러 보고 응답을 판정할 수 있다.
  • 이제 명세대로 도는 백엔드가 있다. 프론트엔드는 이 둘 — docs/API-Spec.md와 돌아가는 백엔드 — 만 있으면 화면을 붙일 수 있다.
