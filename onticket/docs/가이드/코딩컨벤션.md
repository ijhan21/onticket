# 코딩 컨벤션 (TypeScript · React · Hono)

> 버전 1.0 · (주)승승장구 · 모든 TypeScript 프로젝트에 공통 적용한다

## 1. 개요·목적

- **일관성**: 누가(사람이든 AI든) 작성해도 같은 모양의 코드가 나온다.
- **가독성**: 처음 보는 코드도 빠르게 이해한다.
- **유지보수**: 담당자가 바뀌어도 학습 비용이 적다.

원칙적으로 **규칙은 자동화로 강제한다.** 포매팅은 **Prettier**, 정적 검사는 **ESLint**, 타입은 **`tsc --noEmit`**. 셋이 통과하지 않으면 올리지 않는다. 이 문서와 도구 설정이 충돌하면 도구 설정이 우선하고 문서를 고친다.

> 폴더 구조·파일 배치·파일 네이밍은 **[프로젝트 구조]** 문서를 따른다.

## 2. 네이밍

이름은 축약하지 않는다. `qty`가 아니라 `quantity`, `evt`가 아니라 `event`.

| 대상 | 규칙 | 예시 |
|---|---|---|
| 변수·함수 | `camelCase` | `remainingSeats`, `formatPrice()` |
| 컴포넌트 | `PascalCase` | `EventCard`, `TicketQr` |
| 타입·인터페이스 | `PascalCase` | `Order`, `TicketType` |
| 상수 | `UPPER_SNAKE_CASE` | `MAX_QUANTITY_PER_ORDER` |
| boolean | `is`/`has`/`can` 접두 | `isSoldOut`, `hasCheckedIn`, `canRefund` |
| 이벤트 핸들러 | `handle` + 대상 | `handleSubmit`, `handleQuantityChange` |
| 핸들러 prop | `on` + 대상 | `onSelect`, `onConfirm` |

- 도메인 용어는 코드 전체에서 하나로 통일한다. 공연은 `event`, 티켓 등급은 `ticketType`, 주문은 `order`, 티켓은 `ticket`, 입장 확인은 `checkin`. 같은 것을 `show`·`grade`·`booking`으로 섞어 쓰지 않는다. 용어가 늘면 이 표에 먼저 추가한다.

## 3. TypeScript

- **`any`를 쓰지 않는다.** 모르면 `unknown`으로 받고 좁힌다.
- 공개(export) 함수는 **매개변수와 반환 타입을 명시**한다.
- 객체 모양은 `interface`/`type`으로 정의하고 인라인 반복을 피한다.
- `null`/`undefined`는 옵셔널 체이닝·기본값으로 명시 처리. non-null 단언(`!`)은 쓰지 않는다.
- 상태는 리터럴 유니온으로 좁게. `string` 대신 `'판매중' | '매진' | '판매종료'`. 상태값 글자는 회사 데이터(CSV)와 PRD가 정한 그대로 쓰고 영어로 번역하지 않는다. `enum`보다 `as const`·리터럴 유니온을 우선한다.
- **금액은 정수(원 단위)**로만 다룬다. 소수·부동소수 금액 계산 금지.

## 4. React (web)

- **함수형 컴포넌트만.** Hook은 컴포넌트 최상위에서만 호출한다.
- props는 타입을 정의해서 받는다. `React.FC`는 쓰지 않는다.
- **파생 상태를 `useState`로 만들지 않는다.** 계산으로 얻는 값은 렌더링 시 계산한다.
- `useEffect`는 외부 시스템과 동기화할 때만. 렌더링 중 계산이나 이벤트 처리에 쓰지 않는다.
- `key`에 배열 인덱스를 쓰지 않는다. 안정적인 식별자(`event.id`)를 쓴다.
- 상호작용·브라우저 API·훅이 필요할 때만 `'use client'`. 데이터 조회는 가능한 한 서버 컴포넌트에서.
- **색·간격·글자 크기는 디자인 토큰 이름으로만** 쓴다. 컴포넌트에 HEX·px를 직접 적지 않는다.

```tsx
// 좋은 예 — props 타입, 파생값은 계산, 토큰만 사용
interface TicketTypeRowProps {
  name: string;
  price: number;
  remaining: number;
}

export function TicketTypeRow({ name, price, remaining }: TicketTypeRowProps) {
  const isSoldOut = remaining === 0; // 표시용 파생값. 판정은 서버가 한다
  return (
    <li className="flex justify-between text-fg">
      <span>{name}</span>
      <span className="text-accent">{formatPrice(price)}</span>
      {isSoldOut && <span className="text-fg-muted">매진</span>}
    </li>
  );
}
```

## 5. Hono (api)

- 라우트 파일은 리소스 하나만 다룬다. 핸들러는 **검증 → 인증 → 서비스 호출 → 응답 변환**만 한다.
- 모든 입력(body·query·param)은 Zod 스키마로 파싱한 뒤 쓴다. 신뢰하지 않는다.
- 표준 에러 응답 `{ error: { code, message } }`를 `lib/http` 헬퍼로 만든다. 라우트마다 손으로 만들지 않는다.
- `try/catch`로 삼키지 않는다. 사용자에겐 안전한 문구, 로그에는 원인.
- 잔여 수량 차감·결제 승인·입장 확인처럼 **동시에 들어오면 깨지는 작업**은 서비스에서 한 번에 처리한다(DB 수준의 조건부 갱신·잠금). 화면에서 "잔여 확인 → 주문"을 두 번에 나눠 부르지 않는다.

```ts
// src/routes/orders.ts — 핸들러는 얇게
orders.post('/', async (c) => {
  const parsed = createOrderSchema.safeParse(await c.req.json());
  if (!parsed.success) return badRequest(c, 'INVALID_INPUT', '입력값을 확인해 주세요.');
  try {
    const order = await createOrder(parsed.data);          // 서비스: 수량 확인·차감·주문 생성을 한 번에
    return c.json(order, 201);
  } catch (err) {
    if (err instanceof SoldOutError) return conflict(c, 'SOLD_OUT', '남은 수량이 없어요.');
    console.error('createOrder failed', err);
    return internalError(c);
  }
});
```

## 6. 보안·데이터

- **브라우저에서 DB를 직접 호출하지 않는다.** 데이터 접근은 서버(API)만 한다.
- **판정은 서버가 한다.** 잔여 수량·금액·결제 승인 결과·입장 가능 여부를 화면이 계산해 믿지 않는다. 화면은 표시만 한다.
- **비밀값은 코드에 적지 않는다.** 결제 시크릿·DB 서비스 키는 서버 환경변수로만. 브라우저 노출 가능 값만 `NEXT_PUBLIC_`.
- **결제 금액은 서버가 다시 계산**한다. 화면이 보낸 금액을 그대로 승인하지 않는다.
- **`console.log`를 커밋하지 않는다.** 서버의 의도된 로그만 남긴다.

## 7. 포매팅

Prettier가 결정한다. 들여쓰기 스페이스 2, 세미콜론 사용, 홑따옴표, 최대 100컬럼, 여러 줄일 때 후행 쉼표. import 순서: 외부 패키지 → 내부 별칭(`@/`) → 상대경로, 그룹 사이 빈 줄. 한 파일은 한 책임. 300줄을 넘으면 분리를 검토한다.

## 8. 주석

- **'무엇을'이 아니라 '왜'**를 적는다. 코드가 말하는 것을 반복하지 않는다.
- 공개 함수에는 한두 줄 JSDoc.
- `TODO`/`FIXME`는 담당자나 이슈 번호와 함께. 익명 TODO는 방치된다.
