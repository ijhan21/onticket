# Git 커밋 컨벤션 (Conventional Commits)

> 버전 1.0 · (주)승승장구 · 모든 프로젝트에 공통 적용한다

## 1. 개요

빠르게 커밋을 쌓는 만큼 **일관된 커밋 규칙**이 없으면 이력이 금세 어지러워진다. 우리는 [Conventional Commits](https://www.conventionalcommits.org)를 채택한다.

- **이력 추적**: `type(scope)`만 봐도 무엇이 왜 바뀌었는지 파악한다.
- **자동 릴리스 노트**: 커밋 타입을 파싱해 변경 기록을 자동으로 만든다.
- **협업**: 사람과 AI가 같은 문법으로 커밋을 읽고 쓴다.

## 2. 커밋 메시지 형식

```
type(scope): subject

<본문(선택)>

<꼬리말(선택)>
```

- **type**: 변경의 성격(필수). 아래 표.
- **scope**: 변경이 일어난 영역(선택, 소문자).
- **subject**: 요약. **명령형**, 한국어 허용, **50자 내외**, 마침표 없음.
- **본문**: **무엇을**보다 **왜** 바꿨는지. 제목과 한 줄 띄우고 72자 내외로 줄바꿈.
- **꼬리말**: 이슈 연결(`Closes #12`), 파괴적 변경(`BREAKING CHANGE:`).

```
feat(booking): 등급별 잔여 수량 확인 후 주문 생성

결제 직전 서버가 잔여 수량을 다시 확인하지 않아 초과 판매가
가능했던 문제를 막기 위해, 주문 생성 시 수량을 잠그고 검증한다.

Closes #12
```

## 3. type 목록

| type | 의미 |
|---|---|
| `feat` | 새 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 변경(PRD, 화면기획서, ADR, 가이드) |
| `style` | 코드 의미에 영향 없는 포맷 변경 |
| `refactor` | 기능 변화 없는 구조 개선 |
| `test` | 테스트 추가·수정 |
| `chore` | 빌드·설정·의존성 등 잡무 |
| `perf` | 성능 개선 |
| `ci` | CI/CD·배포 설정 변경 |

## 4. scope 예시 (온티켓)

| scope | 영역 |
|---|---|
| `event` | 공연(이벤트) 목록·상세 |
| `booking` | 예매·주문·잔여 수량 |
| `payment` | 결제 요청·승인·실패 처리 |
| `ticket` | 티켓 발급·QR·조회 |
| `checkin` | 현장 입장 확인 |
| `admin` | 운영팀 판매 현황 |
| `ui` | 공통 컴포넌트·토큰·레이아웃 |
| `db` | 스키마·마이그레이션·시드 |
| `api` | API 명세·공통 응답 형식 |
| `deploy` | Vercel·Cloudflare·환경변수 |

## 5. 좋은 예 / 나쁜 예

```
feat(event): 공연 목록 화면에 매진 상태 표시
fix(booking): 잔여 1장일 때 동시 결제 시 한 건만 성공하도록 잠금 추가
docs(api): 주문 생성 API 명세에 409 응답 추가
chore(deploy): Cloudflare Workers 환경변수에 결제 시크릿 이름 추가
```

| 나쁜 예 | 왜 나쁜가 |
|---|---|
| `수정함` | type·scope 없음, 무엇을 고쳤는지 불명 |
| `fix: 버그` | 어떤 버그인지 알 수 없음 |
| `feat(booking): 예매 기능을 추가했습니다.` | 과거형·존댓말, 마침표 |
| `feat: event fix ui refactor` | 한 커밋에 여러 변경 뒤섞음 |

> 한 커밋은 하나의 목적만 담는다. 관련 없는 변경은 나눠 커밋한다.

## 6. 커밋 전 점검 — 비밀값과 환경변수 견본

한 번 올라간 값은 이력에 남아 지워도 사라지지 않는다.

- `.env`, `.env.local` 등 실제 값이 든 파일은 `.gitignore`로 막는다. `git status`에 보이면 진행하지 않는다.
- 값 없이 이름만 적은 견본 `.env.example`을 저장소에 둔다. 환경변수를 추가·삭제했으면 **같은 커밋에서** 견본을 맞춘다.
- 실제 값은 견본에 적지 않는다. 형식을 알려야 하면 가짜 예시를 쓴다.

**커밋 전 점검 목록**
1. `git status`에 비밀값 파일이 없는가
2. 환경변수를 건드렸다면 견본을 갱신했는가
3. 키·토큰·비밀번호를 코드에 직접 적지 않았는가
4. 한 커밋에 하나의 목적만 담겼는가

## 7. 브랜치와 올리기

| 브랜치 | 용도 |
|---|---|
| `main` | 배포 기준. 항상 배포 가능한 상태 |
| `feature/<이름>` | 새 기능 (예: `feature/qr-checkin`) |
| `fix/<이름>` | 버그 수정 (예: `fix/sold-out-race`) |

- 이름은 소문자·하이픈(kebab-case)으로 짧게.
- **혼자 개발할 때**는 `main`에 직접 커밋·푸시해도 된다. 단, 푸시 전 점검 목록(6절)은 그대로 지킨다.
- **둘 이상이 함께 개발할 때**는 브랜치에서 작업하고 PR을 열어 리뷰 1명 승인 후 **Squash and merge**한다. PR 제목은 커밋 컨벤션을 따른다.

작은 규칙이 큰 이력을 만든다. 커밋 하나하나가 팀의 기록이다.
