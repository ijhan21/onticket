# 프로젝트 구조 & 코드 레이어 컨벤션

> 버전 1.1 · (주)승승장구 · **1부 레이어 원칙**은 모든 프로젝트에 공통 적용한다. **2부·3부는 스택별 적용판**이다 — 프로젝트가 어느 스택을 쓰는지는 그 프로젝트의 아키텍처 결정 기록(ADR)이 정한다.
> 모든 프로젝트가 똑같은 파일을 갖지는 않는다. **바뀌지 않는 것은 "레이어의 역할"과 "의존 방향"** 이다.

---

# 1부 — 레이어 원칙 (스택 공통)

## 1.1 레이어와 책임

코드는 역할이 다른 레이어로 나눈다. 각 레이어는 **인접 레이어와만** 대화하고, **의존은 위에서 아래로만** 흐른다.

| 레이어 | 역할 | 하지 않는 것 |
|---|---|---|
| **화면(표현)** | 화면을 그리고 사용자 입력을 받는다. 서버 응답을 표시만 한다 | 비즈니스 로직·데이터 접근 금지 |
| **라우트 핸들러(컨트롤러)** | HTTP 요청/응답, 입력 검증, 인증 확인. 얇게 유지하고 로직은 서비스에 위임 | 복잡한 계산·DB 세부 |
| **서비스(비즈니스 로직)** | 도메인 계산·판정(잔여 수량, 금액, 상태 전이), 외부 API(결제) 호출 조합 | HTTP·DB 접근 세부는 모른다 |
| **데이터 접근(리포지토리)** | DB·외부 API 접근을 한곳에 모은다. 조회·저장 | 비즈니스 규칙 없음 |
| **공용** | 타입, 유틸, 클라이언트 설정 | 도메인 규칙 없음 |

**흐름:** 화면 → 라우트 핸들러 → 서비스 → 데이터 접근 → (DB·외부 API). 화면이 서비스나 DB를 건너뛰어 직접 부르지 않는다.

**왜 나누나:** DB를 바꾸면 데이터 접근 레이어만, 규칙을 바꾸면 서비스만 고친다. 변경의 영향이 한 레이어에 갇힌다.

## 1.2 어디서나 지키는 것

- **의존 방향은 한쪽으로만.** 서비스가 라우트 핸들러를 부르지 않는다.
- **라우트 핸들러는 얇게.** 검증 → 인증 확인 → 서비스 호출 → 응답 변환. 그 이상이면 서비스로 뺀다.
- **데이터 접근은 서버에서만.** 브라우저에서 DB를 직접 부르지 않는다.
- **판정은 서버가 한다.** 금액·잔여 수량·결제 승인·입장 가능 여부를 화면에 맡기지 않는다.
- **비밀값은 코드 밖 환경변수로.**
- **문서와 산출물 폴더는 고정한다.** 입력 데이터 `data/`, 문서 `docs/`, 디자인 산출물 `design/`. 코드 폴더는 스택별 적용판을 따른다.

## 1.3 스택별 대응

| 레이어 | Next.js(App Router) | Hono(Cloudflare Workers) | Python·FastAPI |
|---|---|---|---|
| 라우트 핸들러 | `app/api/**/route.ts` | `src/routes/*.ts` | `routers/*.py` |
| 서비스 | `lib/services/*.ts` | `src/services/*.ts` | `services/*.py` |
| 데이터 접근 | `lib/repositories/*.ts` | `src/repositories/*.ts` | `repositories/*.py` |
| 검증 스키마 | Zod | Zod | Pydantic |

# 2부 — Next.js·TypeScript 적용 (화면, 또는 통합형의 화면+API)

## 2.1 폴더 구조 (예시)

```
app/                   라우트와 페이지 (App Router)
  api/                 (통합형일 때만) API — HTTP 경계
components/            화면 컴포넌트(도메인)
  ui/                  공통 UI 컴포넌트 — 디자인 토큰만 쓴다
lib/
  api-client/          (분리형일 때) API 서버 호출 함수 — 화면은 이것만 부른다
  services/            (통합형일 때) 비즈니스 로직
  repositories/        (통합형일 때) 데이터 접근
  schemas/             요청·응답 검증 스키마
types/                 도메인 타입
```

- `components/ui`는 도메인을 모른다(버튼·입력·카드 같은 공통 조각). 색·간격은 **디자인 토큰 이름**으로만 쓴다.
- 화면은 서버 응답을 표시만 한다. 잔여 수량·금액·매진 여부를 화면에서 계산해 판정하지 않는다.
- 경로는 별칭 `@/`로 참조한다.

## 2.2 환경변수

- 비밀값은 `.env.local`에 두고 저장소에 올리지 않는다. 견본은 `.env.example`.
- 브라우저 노출용은 `NEXT_PUBLIC_` 접두. 서버 전용 키(DB 서비스 키, 결제 시크릿)에는 절대 붙이지 않는다.
- 이름은 아래 표로 고정한다. 다른 이름을 새로 짓지 않는다.

| 이름 | 어디에 | 뜻 |
|---|---|---|
| `NEXT_PUBLIC_API_URL` | web `.env.local` | 화면이 부르는 API 서버 주소 (로컬은 `http://localhost:8787`) |

# 3부 — Hono·Cloudflare Workers 적용 (분리형의 API 서버)

## 3.1 폴더 구조 (예시)

```
src/
  index.ts             앱 진입점 — 라우트 등록, 공통 미들웨어
  routes/              라우트 핸들러 — 리소스 단위 파일
  services/            비즈니스 로직 (잔여 수량·금액·상태 판정, 결제 승인 조합)
  repositories/        데이터 접근 (Supabase)
  schemas/             Zod 검증 스키마
  lib/
    http.ts            공통 에러 응답·상태코드 헬퍼
    auth.ts            운영팀 인증 확인 헬퍼
wrangler.toml          Workers 설정 (비밀값은 넣지 않는다)
.env                   로컬 비밀값 — 저장소에 올리지 않는다 (견본 .env.example)
```

## 3.2 라우트 규칙

**리소스 단위로 나눈다.** 동사를 경로에 넣지 않는다(`/api/getEvents` ✗). **운영팀 전용 경로는 전부 `/admin/` 아래에 둔다.** 같은 리소스라도 고객이 보는 것과 운영팀이 다루는 것은 경로가 다르다.

```
/health                     GET(서버 확인)
/events                     GET(목록)
/events/:id                 GET(상세)
/orders                     POST(생성)
/orders/:id                 GET(조회) — 소유 확인 값은 쿼리로(?buyer_email=)
/payments/confirm           POST(승인) — 외부 결제사 콜백·승인 같은 행위는 하위 리소스로
/admin/events               GET(운영: 목록·현황) / POST(운영: 등록)
/admin/events/:id           GET(운영: 조회) / PUT(운영: 수정)
/admin/checkins             POST(운영: 입장 확인)
```

**운영팀 인증은 공유 비밀번호 한 개를 머리(header)로 받는다.** `/admin/` 아래의 모든 요청은 `X-Admin-Password: <비밀번호>` 머리를 싣는다. 서버는 환경변수 `ADMIN_PASSWORD`와 비교해 없거나 다르면 `401`을 돌려주고 데이터를 싣지 않는다. 로그인 엔드포인트·세션·토큰을 두지 않는다. 운영자 입장 화면은 입력받은 비밀번호로 `GET /admin/events`를 한 번 불러 `200`이면 통과, `401`이면 틀린 것으로 본다.

**라우트 핸들러는 네 가지만 한다.** 그 이상이면 서비스로 뺀다.
1. **입력 검증** — `schemas`의 Zod 스키마로 파싱. 실패하면 `400`.
2. **인증 확인** — 운영팀 전용 경로는 `lib/auth`로 확인. 없으면 `401`.
3. **서비스 호출** — 도메인 로직은 전부 서비스가 한다.
4. **응답 변환** — 서비스 결과를 응답 형태로 바꿔 돌려준다.

**에러 응답은 한 형식으로 통일한다.** `{ error: { code, message } }` + 상태코드. 각 라우트에서 제각각 만들지 않고 `lib/http` 헬퍼를 쓴다.

| 상황 | 상태코드 |
|---|---|
| 성공(조회·수정) / 생성 | `200` / `201` |
| 입력이 잘못됨 | `400` |
| 인증 필요 / 권한 없음 | `401` / `403` |
| 대상 없음 | `404` |
| 상태 충돌(매진, 이미 입장, 이미 결제) | `409` |
| 서버 오류 | `500` |

## 3.3 환경변수

- 로컬은 `api/.env`, 배포는 Workers 시크릿. 로컬 비밀값은 `.env` 한 파일에만 둔다(`.dev.vars`를 함께 두면 `.env`를 읽지 않는다). 둘 다 코드와 `wrangler.toml`에 적지 않는다.
- 결제 시크릿 키·DB 서비스 키는 API 서버에만 둔다. 화면(web)에는 공개 가능한 값만 간다.
- 이름은 아래 표로 고정한다. 다른 이름을 새로 짓지 않는다.

| 이름 | 뜻 |
|---|---|
| `DATABASE_URL` | DB 연결 문자열 |
| `ADMIN_PASSWORD` | 운영팀 공유 비밀번호 (3.2절 `X-Admin-Password` 머리와 비교) |
| `WEB_ORIGIN` | CORS로 허용할 화면(web) 출처 (로컬은 `http://localhost:3000`) |
| `TOSS_SECRET_KEY` | 결제사 시크릿 키 (결제를 붙일 때) |

## 4. 네이밍 규칙 (공통)

| 대상 | 규칙 | 예시 |
|---|---|---|
| 폴더 | kebab-case | `event-list/` |
| 컴포넌트 파일 | PascalCase + `.tsx` | `EventCard.tsx` |
| 훅 | `useX` + camelCase | `useRemainingSeats.ts` |
| 서비스·유틸·리포지토리 | camelCase + `.ts` | `orderService.ts`, `formatPrice.ts` |
| 검증 스키마 | `<리소스>Schema.ts` | `orderSchema.ts` |
| 타입 | 도메인 이름 | `order.ts` |
| 프레임워크 예약 파일 | 규칙 그대로 | `page.tsx`, `route.ts`, `index.ts` |

## 5. 요약

- 레이어 원칙(1부)은 스택과 무관하게 지킨다. 폴더·네이밍은 스택별 적용판(2부·3부)을 따른다. 어느 적용판을 쓰는지는 ADR이 정한다.
- API 라우트는 **리소스 단위**, 운영팀 경로는 **`/admin/` 아래**, 핸들러는 **검증 → 인증 → 서비스 호출 → 응답 변환**만. 운영팀 인증은 `X-Admin-Password` 머리 하나.
- 환경변수 이름은 2.2·3.3의 표에서만 쓴다.
- 에러 형식과 상태코드는 공통 헬퍼로 통일. 상태 충돌은 `409`.
- 데이터 접근과 판정은 서버에서만. 비밀값은 코드 밖.
