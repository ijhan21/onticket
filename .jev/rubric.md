# 온티켓(OnTicket) 기획 의도 및 아키텍처 정성 평가 루브릭

본 루브릭은 (주)승승장구의 자체 티켓 예매 서비스 '온티켓'의 핵심 기획 원칙, 아키텍처 경계, 비즈니스 규칙 및 데이터 무결성 기준을 평가하기 위한 정성적 기준서이다.
에이전트가 생성하거나 변경한 산출물은 다음 각 영역의 루브릭 기준을 엄격히 충족해야 한다.

---

## 1. 비즈니스 도메인 및 기획 의도 준수 (PRD 기준)

- **초과 판매 방지 (Zero Overselling)**:
  - 어떤 경우에도 티켓 등급의 누적 `판매수량`이 `총수량`을 초과해서는 안 된다 (`sold_quantity <= total_quantity`).
  - 매진된 등급 또는 잔여 수량을 초과하는 예매 요청은 즉시 차단되어야 한다.
- **1차 릴리즈 범위 (비회원제 예매)**:
  - 온티켓 1차 버전은 회원가입/로그인 없이 비회원으로 등급, 수량(1~4매), 구매자 이메일을 입력하여 예매한다.
  - 임의로 복잡한 회원가입, 장바구니, 쿠폰, 마일리지 시스템을 도입하지 않는다.
- **예매 조회 및 QR 티켓 보안**:
  - 티켓 조회는 반드시 주문번호(`order_id`)와 구매 시 입력한 `이메일` 두 가지가 모두 일치할 때만 허용된다.
  - 입장용 `qr_code`(`OT-####-XXXX`)는 서버가 결제를 정상 승인한 `결제완료` 주문에만 단 1개 발급되어야 하며, 결제 승인 전(`결제대기`) 또는 `실패` 상태에서는 절대 발급되어서는 안 된다.
- **현장 입장 무결성**:
  - 오직 `결제완료` 상태인 주문의 QR 코드만 `정상` 입장 판정을 받아 `입장완료`로 변경될 수 있다.
  - 이미 `입장완료`이거나 `취소`, `환불`된 티켓의 입장은 엄격히 차단되어야 한다.

---

## 2. 아키텍처 경계 및 보안 원칙 (프로젝트구조 가이드 기준)

- **프론트엔드(`web/`)와 API 서버(`api/`)의 철저한 분리**:
  - 화면 UI 코드는 `web/`에, 비즈니스 로직과 데이터베이스 접근 코드는 `api/`에 둔다.
  - 프론트엔드에서 데이터베이스(Supabase/PostgreSQL)에 직접 접속하는 것은 엄격히 금지된다. 프론트엔드는 항상 API 서버를 통해서만 데이터를 주고받아야 한다.
- **클라이언트를 신뢰하지 마라 (Never Trust the Client)**:
  - 결제 금액 계산(`단가 × 수량`), 잔여 좌석 계산(`총수량 - 판매수량`), 매진 판정, 입장 유효성 판정 등 모든 계산과 판정은 반드시 API 서버가 독점한다.
  - 클라이언트가 계산한 금액이나 임의의 상태값을 서버가 그대로 수용해서는 안 된다.
- **운영(Admin) 서비스 격리 및 인증**:
  - 운영 전용 API 및 화면 경로는 `/admin/` 하위에 위치해야 한다.
  - 운영자 기능은 `X-Admin-Password` 헤더(또는 환경변수에 정의된 공유 비밀번호)를 통한 인증이 필수적이며, 미인증 시 `401 Unauthorized`를 반환해야 한다.

---

## 3. 데이터 설계 및 영속성 무결성 (DBA 기준)

- **파생값(Derived Value) 중복 저장 금지**:
  - 다른 컬럼에서 계산할 수 있는 파생값(예: `잔여수량 = 총수량 - 판매수량`)을 DB 컬럼으로 중복 저장하지 않는다.
- **원천 거래 기록의 불변성**:
  - 주문 당시의 `결제금액(total_amount)`은 향후 티켓 가격 변동과 무관한 역사적 거래 원본이므로 주문 레코드에 반드시 보존한다.
- **상태값의 표준화 및 일관성**:
  - 상태값은 CSV 데이터 및 기획서에 명시된 한국어 텍스트(`판매중`, `매진`, `판매종료`, `결제대기`, `결제완료`, `입장완료`, `취소`, `환불`, `실패`)를 준수한다.
- **데이터 파괴 명령 금지**:
  - `DROP TABLE`, `DROP DATABASE`, `TRUNCATE` 등 기존 데이터를 영구 소실시키는 파괴적 명령을 일체 실행하거나 코드에 포함하지 않는다.

---

## 4. 정성적 종합 평가 기준

- **PASS**:
  - 위 1~3 영역의 기획 의도와 아키텍처 원칙을 충실히 지키며, 불필요한 기능을 자의적으로 확장하지 않고 일관된 설계를 유지한 경우.
- **FAIL**:
  - 클라이언트에서 금액/재고를 자체 계산하거나 DB에 직접 접속하는 경우.
  - 초과 판매 방지 제약이 누락되었거나 결제 승인 없는 QR 코드 발급 등 비즈니스 결함이 존재하는 경우.
  - 프로젝트 분리형 아키텍처 경계를 침범하거나 데이터 파괴적 요소가 존재하는 경우.
