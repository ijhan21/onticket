# ADR-001: 프론트엔드와 API 서버를 분리한다

- 날짜: 2026-11-07
- 상태: 승인됨 (Accepted)
- 결정자: 개발 리더

| 버전 | 날짜 | 바꾼 것 | 결정자 |
|---|---|---|---|
| 1.0 | 2026-11-07 | 프론트엔드(Next.js)와 API 서버(Hono/Cloudflare) 분리 결정 채택 | 개발 리더 |
| 1.1 | 2026-11-07 | API 명세(docs/API-Spec.md v1.0) 확정 반영: 9개 REST 엔드포인트 규격, `/admin/` 격리 및 `X-Admin-Password` 인증 연계 명시 | 아키텍트 |

---

## 1. 맥락 (Context)

- (주)승승장구 온티켓 1차 버전은 '리버사이드 재즈' 티켓 오픈 전까지 3일 안에 출시해야 한다.
- 개발 인력은 개발 리더 1인이며, 서버비는 월 0원(무료 티어)으로 유지해야 한다.
- 과거 '골목 라이브' 행사에서 수기 명단 확인과 초과 판매, 결제 미확인 입장이 발생했던 사고를 방지해야 한다.
- 특히 정각 오픈 시 순간적인 트래픽 폭주에 안정적으로 대응해야 하며, "클라이언트를 신뢰하지 마라(Never trust the client)" 원칙에 따라 잔여석과 결제 금액 판정의 조작을 원천 차단해야 한다.
- 향후 모바일 앱 출시 및 타 기획사 입점 등 클라이언트 확장 가능성이 제기되었다.

---

## 2. 결정 (Decision)

프론트엔드와 API 서버를 별도 프로젝트로 분리하여 구축하고 각각 배포한다.

- **화면(프론트엔드)**: `web/` 디렉터리에 Next.js(App Router)로 구성하고 Vercel에 배포한다.
- **API 서버**: `api/` 디렉터리에 Hono 프레임워크로 작성하고 Cloudflare Workers에 서버리스로 배포한다.
- **데이터베이스**: Supabase(관리형 PostgreSQL)를 사용한다.
- **판정 독점**: 프론트엔드는 데이터 표시와 사용자 입력만 담당하며, 잔여석 계산·금액 판정·입장 확인 등 모든 비즈니스 규칙과 데이터 접근은 `api/`가 독점한다.
- **API 명세 연계**: `docs/API-Spec.md`(v1.0)에 정의된 9개 REST 엔드포인트를 준수하며, 운영자 경로는 `/admin/`으로 격리하고 `X-Admin-Password` 헤더 인증을 필수화한다.

### 결정 이유 (사람의 결정 근거)
1. **판정의 서버 독점 (구조적 강제)**: 화면과 서버를 물리적으로 분리하여, 클라이언트에서 DB에 직접 접근하거나 금액·재고를 임의 계산하는 설계를 구조적으로 원천 차단하기 위함.
2. **향후 확장성 확보**: "API 서버 하나에 클라이언트 여럿" 구조를 통해, 향후 모바일 앱(iOS/Android) 출시나 타 기획사 입점 시스템이 추가되어도 동일한 API 서버를 그대로 재사용하기 위함.
3. **실무형 구조 습득**: 현업 회사들이 실제로 채택하고 있는 멀티 티어 분리형 아키텍처를 몸에 익히기 위함.

---

## 3. 검토한 대안 (Alternatives Considered)

### 통합형 (Next.js Monolith — 화면 + API 단일 프로젝트, Vercel 단일 배포)
- **장점**:
  - 프로젝트가 1개이고 저장소 설정, 빌드, 배포가 1회로 단순함.
  - 동일 오리진이므로 CORS(교차 출처 리소스 공유) 설정이 불필요함.
  - 3일이라는 극도로 짧은 일정에서 가장 빠르게 서비스를 시작할 수 있음.
- **선택하지 않은 이유**:
  - 화면 코드와 API 코드가 한 프로젝트에 공존하여, 촉박한 일정 속에서 "화면에서 판정하고 처리하자"는 유혹에 빠져 경계가 무너지기 쉬움.
  - 무료 티어 서버리스 환경에서 정각 오픈 시 콜드 스타트(Cold Start) 지연이 발생할 수 있음.
  - 추후 모바일 앱이나 외부 연동이 필요해질 때, 프레임워크 내부에 얽힌 API를 다시 뜯어내 분리하는 대규모 리팩터링 비용이 발생함.

---

## 4. 결과 및 감수하는 것 (Consequences)

### 얻는 것 (이점)
- **규칙의 물리적 강제**: 프론트엔드 코드베이스에는 판정 로직과 DB 접근 코드가 위치할 자리조차 없으므로, 레이어 원칙이 사람의 의지가 아닌 구조로 지켜짐.
- **순간 폭주 대응 및 비용 0원 달성**: Cloudflare Workers의 전 세계 엣지 네트워크를 통해 콜드 스타트 없는 즉각적인 응답이 가능하며, 하루 10만 건 무료 티어 구간 내에서 안정적으로 방어 가능.
- **높은 확장성**: 기존 API 서버 변경 없이 새로운 웹 클라이언트나 모바일 앱을 자유롭게 연결 가능.

### 감수하는 것 (실제 발생하는 비용과 트레이드오프)
- **프로젝트 2개 관리 부담**: `web/`과 `api/`의 `package.json`, TypeScript 설정, 의존성 패키지, 린터 설정을 각각 따로 유지·관리해야 함.
- **배포 2회 및 파이프라인 분리**: Vercel(웹)과 Cloudflare Workers(API) 두 곳의 배포 도구(`vercel`, `wrangler`)와 환경변수를 개별 관리해야 함.
- **CORS 설정 및 디버깅 비용**: 로컬 환경(`localhost:3000` ↔ `localhost:8787`)과 프로덕션 환경(`*.vercel.app` ↔ `*.workers.dev`)에서 CORS 허용 헤더를 반드시 설정해야 하며, 통신 차단 시 디버깅 공수가 추가됨.
- **1인 개발자의 초기 셋업 비용**: 단일 프로젝트보다 초기 프로젝트 뼈대 구축 및 연결 검증에 더 많은 시간이 소요됨.
